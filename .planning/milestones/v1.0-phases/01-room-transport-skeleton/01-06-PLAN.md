<objective>
Build the one piece of this phase most likely to produce a subtle, hard-to-debug bug: the unified alarm scheduler, plus the versioned persistence layer it and everything else depends on.

Purpose: A Durable Object has exactly ONE alarm slot — `ctx.storage.setAlarm` overwrites any pending alarm. Three independent timers (idle GC, host-transfer grace, seat-release grace) implemented naively would silently clobber each other, and the symptom would be "sometimes the host never transfers", weeks later. Building the scheduler as a pure, fake-timer-testable function set first makes that failure impossible by construction.
Output: `apps/worker/src/scheduler.ts` and `apps/worker/src/persistence.ts` with full unit coverage.
</objective>

Create `apps/worker/src/scheduler.ts` as pure functions over a plain array — no `ctx.storage`, no `setAlarm`, no `Date.now()`. Plan 07 is the only place that touches the real alarm API; everything decidable is decided here so it can be tested with explicit timestamps.

Define `type TimerEvent = { type: TimerType; dueAt: number; seatId?: string }` where `TimerType` is the closed union `"idle_gc" | "host_transfer" | "seat_release"`. Timers are keyed by `type` plus `seatId` — there is at most one `idle_gc` and at most one `host_transfer` per room, and at most one `seat_release` per seat.

Export:
- `upsertTimer(timers, event): TimerEvent[]` — replaces any existing timer with the same key, returning a new array sorted ascending by `dueAt`.
- `cancelTimer(timers, type, seatId?): TimerEvent[]`
- `nextDueAt(timers): number | null` — the minimum `dueAt`, or `null` when the table is empty. This is the single value Plan 07 passes to `ctx.storage.setAlarm`, and `null` means "delete the alarm".
- `dueTimers(timers, now): { due: TimerEvent[]; remaining: TimerEvent[] }` — partitions on `dueAt <= now`. `onAlarm` processes ALL due events in one wake, not just the earliest, because a single alarm firing may coincide with several deadlines.
- `computeRoomTimers(state: RoomState, now: number): TimerEvent[]` — derives the complete timer table from room state alone. This is the key design choice: rather than incrementally mutating timers at each event and hoping the mutations stay consistent across hibernation, the whole table is RECOMPUTED from persisted state after every state change. A recomputed table cannot drift, and it makes `onStart` idempotent for free (Pitfall 2). The derivation rules:
  * always one `idle_gc` at `state.lastActivityAt + (state.status === "in_progress" ? IDLE_GC_IN_PROGRESS_MS : IDLE_GC_LOBBY_MS)` — 12 hours vs 1 hour per D-02;
  * one `host_transfer` at `hostSeat.disconnectedAt + HOST_TRANSFER_GRACE_MS` **only when** `state.status === "lobby"`, the host seat exists, and it is disconnected — D-07 scopes host transfer to the lobby, so an in-progress game never reassigns the host on a dropped connection;
  * one `seat_release` per disconnected seat at `seat.disconnectedAt + LOBBY_SEAT_RELEASE_GRACE_MS` **only when** `state.status === "lobby"` — D-12 frees abandoned lobby seats; in-progress seats are never auto-released in this phase (that is Phase 5's territory and releasing one mid-game would violate the core "does not lose their seat" promise).

`computeRoomTimers` reads the per-seat `disconnectedAt: number | null` field that Plan 03 defined on `SeatSchema` — it is persisted precisely so a grace-period deadline survives a hibernation eviction. Treat `packages/schema` as read-only from this plan; if the field is missing, that is a Plan 03 regression, so fix it there and note it in the SUMMARY rather than shadowing it with a local type here.

Write `scheduler.test.ts` using explicit timestamps (no fake timers needed since nothing reads the clock):

Pitfall 1 regression — the central test. Build a state with a disconnected lobby host AND activity 59 minutes ago, so `host_transfer` and `idle_gc` are both pending. Assert `computeRoomTimers` returns BOTH, that `nextDueAt` is the host transfer (the sooner one), and that after processing the host transfer the recomputed table still contains the idle GC. Name this test literally "unified scheduler: host transfer does not clobber idle GC (RESEARCH Pitfall 1)".

D-02 — a lobby room idle for 59m59s yields no due timers; at 60m00s `idle_gc` is due. An in-progress room idle for 11h59m yields none; at 12h it is due. Assert against the imported constants, not hardcoded numbers, so a constant change fails here loudly.

D-07 — a disconnected lobby host produces a `host_transfer` at exactly +45s; a disconnected host in an `in_progress` room produces NO `host_transfer`; a connected host produces none.

D-12 — a disconnected lobby seat produces a `seat_release` at +30s; a disconnected in-progress seat produces none.

Idempotency — calling `computeRoomTimers` twice on the same state returns deep-equal arrays (simulating repeated hibernation wakes), and `nextDueAt` is stable across those calls, so a wake can never push the deadline forward (Pitfall 2's failure mode).

`dueTimers` — with three timers at t=10, t=20, t=30 and `now=25`, returns two due and one remaining.

Create `apps/worker/src/persistence.ts` operating against a narrow injected storage interface — `type RoomStorage = { get<T>(key: string): Promise<T | undefined>; put(key: string, value: unknown): Promise<void>; delete(key: string): Promise<boolean>; deleteAll(): Promise<void> }` — so tests use an in-memory Map and the Durable Object passes `this.ctx.storage` in Plan 07. Do not import anything Cloudflare-specific here.

Export `STORAGE_KEYS = { schemaVersion: "schemaVersion", room: "room", timers: "timers" } as const`. The version MUST be its own top-level key, read BEFORE the room blob — Pitfall 3: storing the version inside the blob means you have to parse untrusted old-shaped data just to discover you should not have parsed it.

Export `loadRoom(storage, fallback: () => RoomState): Promise<{ room: RoomState; wasReset: boolean }>`:
1. Read `schemaVersion`. If it is `undefined` (fresh room) or `!== ROOM_SCHEMA_VERSION`, do NOT read or parse the room blob at all. Call `storage.deleteAll()`, write the current `schemaVersion`, build a fresh room from `fallback()`, persist it, and return `wasReset: true`.
2. Otherwise read the room blob and validate it with `RoomStateSchema.safeParse`. On a parse failure — which means storage is corrupt despite a matching version — take the same reset path and return `wasReset: true`. D-17's stated preference is explicit: a friend group can re-click a link; a corrupted mid-game state is worse.
3. Return the parsed room with `wasReset: false`.

Export `saveRoom(storage, room, timers): Promise<void>` writing the room blob and the timer table, validating the room with `RoomStateSchema.parse` first so a server-side shape bug is caught at write time rather than being discovered on a later load. Export `loadTimers(storage)` returning `[]` when absent.

`loadRoom` must be safe to call on every hibernation wake — it reads and returns, and never arms an alarm (Pitfall 2). Add a comment saying so explicitly, since `onStart` is where the tempting mistake lives.

Write `persistence.test.ts` against a `Map`-backed fake storage:
- Fresh storage: `loadRoom` returns `wasReset: true`, writes `ROOM_SCHEMA_VERSION`, and the persisted room deep-equals the fallback.
- Round trip: `saveRoom` then `loadRoom` returns `wasReset: false` and a deep-equal room.
- D-17 mismatch: seed `schemaVersion: 0` plus a garbage room blob containing keys the current schema does not have; `loadRoom` returns `wasReset: true`, the resulting room is an empty lobby with zero seats, and — the important assertion — the fake storage records ZERO `get` calls for the `room` key, proving the old blob was never parsed. Name this test literally "D-17: version mismatch resets without reading the old blob".
- Corrupt-but-versioned: matching version with a room blob that fails `RoomStateSchema` returns `wasReset: true` rather than throwing.
- Idempotent wake: calling `loadRoom` three times in a row on a healthy room returns identical results and performs no writes after the first.
- `saveRoom` with a malformed room throws before writing anything (assert storage is unchanged).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| previous deploy's persisted state → current code | Bytes written by an older schema are untrusted input to the running version (D-17) |
| wall-clock time → room lifecycle | Timers decide when rooms are destroyed and when host control moves |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-12 | Tampering | `loadRoom` | mitigate | `schemaVersion` lives under its own storage key and is checked BEFORE the room blob is read. A mismatch triggers `deleteAll()` + fresh lobby with the old bytes never deserialized (D-17, Pitfall 3). A matching-version-but-unparseable blob takes the same reset path rather than throwing inside a DO wake. |
| T-1-18 | Denial of Service | unified alarm scheduler | mitigate | `computeRoomTimers` derives the full table from state on every change, so a lost or duplicated incremental mutation cannot leave an orphan alarm or a permanently deferred deadline. The Pitfall 1 regression test asserts co-existing timers; the idempotency test asserts a hibernation wake cannot push a deadline forward (Pitfall 2). |
| T-1-19 | Denial of Service | abandoned rooms | mitigate | Idle GC at 1h (lobby) / 12h (in-progress) bounds Durable Object storage growth on a Free plan with a 5GB total cap — ROOM-08 is as much a cost control as a hygiene feature. Thresholds are derived from `lastActivityAt`, not from creation, so an active 25-minute game is never collected. |
| T-1-20 | Elevation of Privilege | `host_transfer` timer | mitigate | Host transfer is scoped to `status === "lobby"` only, moves control to the earliest-joined connected seat deterministically (no client input), and cannot fire mid-game. A malicious client cannot induce a transfer other than by causing the real host's socket to close. |
| T-1-21 | Denial of Service | premature seat release | mitigate | `seat_release` is lobby-only. In-progress seats are never auto-released in this phase, which is what makes "a sleeping tab for several minutes does not cost someone their seat" structurally true rather than a tuning accident. |
</threat_model>
