  <action>
`apps/web/lib/seat-token.ts` — export `seatTokenKey(code: string)` returning `` `room:${code}` ``, plus `readSeatToken`, `writeSeatToken`, `clearSeatToken`. Every function must be safe to call during SSR: guard on `typeof window === "undefined"` and return `undefined`/no-op, and wrap access in try/catch because `localStorage` throws in private-mode Safari and with storage disabled. A thrown storage error must degrade to "no saved seat" — the player re-enters their name — never to a crashed page.

`apps/web/lib/room-store.ts` — a Zustand store holding exactly `{ view: RoomView | null, status: "connecting" | "joining" | "seated" | "refused" | "superseded", refusalReason: RefusalReason | null, seatId: string | null }` and the reducers that apply each `ServerMessage`. Keep it a thin cache of the last server-pushed view — the server is authoritative, and the client must never compute or patch room state locally. Write `room-store.test.ts` covering each `ServerMessage` variant's effect on the store, including that a `refused` message clears `view` to `null` (a refused arrival must not be left rendering stale seats).

`apps/web/lib/room-socket.ts` — export `useRoomSocket({ code, displayName })`. It opens a `partysocket` connection to `NEXT_PUBLIC_WORKER_HOST` with `party: "room"` and `room: code`, relying entirely on partysocket's built-in reconnect/backoff (`minReconnectionDelay`, `maxReconnectionDelay`, `reconnectionDelayGrowFactor`) — do NOT hand-roll a retry loop; RESEARCH § Don't Hand-Roll flags that as a thundering-herd risk after a real outage.

On every `open` — including every automatic reconnect, not just the first — send `{ type: "join", displayName, seatToken: readSeatToken(code) }`. One code path for first join and for reconnect is what RT-05 will require in Phase 5; building two paths now is the thing that would have to be undone.

Validate every inbound frame with `ServerMessageSchema.safeParse` before touching the store, and ignore anything that fails rather than throwing. On `joined`, call `writeSeatToken(code, msg.seatToken)` and set `seatId`. On `refused`, set status `refused` with the reason and do not reconnect. On `superseded`, set status `superseded` and close the socket without reconnecting — otherwise partysocket's backoff would fight the newer tab in a loop, which is exactly the corruption D-08 is meant to avoid; disable reconnection explicitly on this path.

Add `NEXT_PUBLIC_WORKER_HOST` to `apps/web/.env.example` with the `wrangler dev` default (`localhost:8787`) and a comment naming the production `*.workers.dev` host that Plan 11 fills in.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Worker → browser (WebSocket frame) | The client must not trust frame shape blindly, even from its own server, because a version-skewed deploy is indistinguishable from a hostile frame |
| browser localStorage → join message | The seat token is a bearer credential living in a store the user (and any same-origin script) can read |
| host-only controls | Rendered conditionally in the client, but authorised only server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-03 | Tampering | `room-socket.ts` inbound frames | mitigate | Every frame runs through `ServerMessageSchema.safeParse` before reaching the store; failures are ignored rather than thrown, so a skewed deploy degrades to a stale view instead of a crashed tab. |
| T-1-25 | Elevation of Privilege | host-only UI controls | mitigate | Hiding the variant picker and Start button for non-hosts is presentation only. Authorisation lives in `room-state.ts` (`not_host`) and is integration-tested in Plan 07; a user who un-hides the control via devtools gets a `not_host` error, not a state change. Stated here so no later phase mistakes the client check for the control. |
| T-1-26 | Information Disclosure | seat token in `localStorage` | accept | D-05 chose `localStorage` deliberately: the token must survive a refresh and a sleeping tab, which rules out in-memory storage, and it is a seat claim rather than an authentication credential. Same-origin script access is an accepted risk given no accounts, no PII and a friend-group threat model. Scoped per room code so one room's token cannot claim a seat in another. |
| T-1-02 | Tampering | second-tab reconnect loop | mitigate | On `superseded` the client disables partysocket reconnection and closes, so two tabs cannot fight over one seat in a backoff loop. Verified in step 10 of the human check. |
| T-1-27 | Denial of Service | reconnect storm | mitigate | Reconnect/backoff is delegated entirely to `partysocket` (jittered, growth-factored); a hand-rolled retry loop is grep-forbidden, per RESEARCH § Don't Hand-Roll. |
</threat_model>
