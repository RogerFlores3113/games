<objective>
Define the wire protocol and the persisted room-state shape once, in a package both the Cloudflare Worker and the Next.js client import, so the two runtimes cannot drift.

Purpose: Messages cross a boundary between two separately-deployed runtimes. A shared Zod schema is simultaneously the runtime input-validation layer (ASVS V5 / threat T-1-03), the compile-time type source, and the documentation of the protocol. It is also where the D-01 room code and the D-05 seat token are made structurally distinct, which is the RT-07 seat-hijack boundary.
Output: `@games/schema` exporting message schemas, room-state schemas, view types and every tuning constant in this phase.
</objective>

Further, `seatId` is a stable internal id, `displayLabel` is the D-09 auto-suffixed rendering (`"Roger (2)"`) and `displayName` is what the player typed. Add a doc comment on `PublicSeatSchema` stating that Phase 2 hardens this whitelist-serialize discipline for game state; the seat records already follow it.

Create `packages/schema/src/messages.ts`.

`ClientMessageSchema` is a `z.discriminatedUnion("type", ...)` over exactly these members, in `strict()` object mode so unknown keys are rejected rather than stripped:
- `{ type: "join", displayName: DisplayName, seatToken?: SeatToken }` — the seat token is optional; presence means "reclaim", absence means "new join" (D-05, ROOM-02).
- `{ type: "set_variant", variant: Variant }` — host-only, lobby-only (D-13, ROOM-05).
- `{ type: "start_game" }` — host-only (D-10, ROOM-06).
- `{ type: "game_action", request: z.unknown() }` — the payload is deliberately `unknown` here and is validated by the game adapter, not by this schema. Add a comment explaining why: the schema package must not know what a game action is (FDN-01), and the adapter already treats `request` as hostile input.
- `{ type: "leave" }` (D-12).

There is intentionally NO client message that carries room state, seat assignment, host identity, or a display label. A client can request actions; it can never assert results. State that assertion in a file-level comment — it is the T-1-04/HIDE-05 boundary later phases must not erode.

`ServerMessageSchema` is a `z.discriminatedUnion("type", ...)` over:
- `{ type: "joined", seatId, seatToken, view: RoomView }` — the ONLY message that ever carries a seat token, and it is sent to exactly the one connection that just claimed the seat.
- `{ type: "state", view: RoomView }` — every subsequent per-seat push.
- `{ type: "refused", reason: RefusalReason }` (D-06, D-14).
- `{ type: "superseded" }` — sent to a stale tab before closing it with `SUPERSEDED_CLOSE_CODE` (D-08).
- `{ type: "error", code: RefusalReason, detail?: string }` — for rejected actions that are not a join refusal.

Export `parseClientMessage(raw: string): { ok: true; message: ClientMessage } | { ok: false; reason: "bad_request" }` — it must `JSON.parse` inside a try/catch, run `ClientMessageSchema.safeParse`, and NEVER throw. The Durable Object calls exactly this function; an exception escaping a message handler tears down connections for the whole room. Also export `encodeServerMessage(msg: ServerMessage): string` which validates with `ServerMessageSchema.parse` before stringifying, so a server-side shape bug is caught at the send site rather than mis-rendered in a browser.

Write `messages.test.ts` covering: a valid join with and without a seat token; a join with an extra unknown key is rejected (proving `strict()`); `parseClientMessage("not json")` returns `{ok:false, reason:"bad_request"}` without throwing; a fast-check property over `fc.string()` asserting `parseClientMessage` never throws for any input; a `game_action` with an arbitrary nested payload parses successfully (the adapter, not this schema, judges it); and `encodeServerMessage` throws for a malformed server message.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Durable Object (WebSocket frame) | Untrusted JSON text arrives on every message; `parseClientMessage` is the sole entry gate |
| persisted DO storage → running code | State written by a PREVIOUS deploy is untrusted input to the current one (D-17) |
| server state → browser | `RoomView`/`PublicSeat` are the only shapes permitted to cross outward |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-03 | Tampering | `parseClientMessage` | mitigate | Closed `z.discriminatedUnion` in `strict()` mode rejects unknown message types and unknown keys before dispatch (ASVS V5). Wrapped in try/catch so malformed JSON returns `bad_request` instead of throwing inside the DO message handler. |
| T-1-04 | Elevation of Privilege | `ClientMessageSchema` | mitigate | No client message carries `seatId`, `hostSeatId`, `status`, or `displayLabel`. Seat identity is derived server-side from the seat token only; host status is derived from persisted `hostSeatId`. Asserted by the "client cannot assert its own seat id" test. |
| T-1-01 | Spoofing | `SeatTokenSchema` vs `RoomCodeSchema` | mitigate | Two branded types with different lengths and alphabets: 6 chars over a 32-char speakable alphabet for the shareable code, 24 chars over nanoid's 64-char alphabet (~143 bits) for the private seat credential. The brand makes conflating them a compile error. |
| T-1-11 | Information Disclosure | `PublicSeatSchema` | mitigate | Declared independently rather than derived by `.omit()` from `SeatSchema`, so a field added to the persisted seat record (including `seatToken`) cannot leak into the client view by default. Test asserts the exact key set. |
| T-1-12 | Tampering | persisted state from an older deploy | mitigate | `ROOM_SCHEMA_VERSION` is a standalone exported constant stored under its own storage key (Plan 06), so a mismatch is detectable WITHOUT parsing the untrusted blob — Pitfall 3. D-17: reset to empty lobby, never migrate. |
</threat_model>
