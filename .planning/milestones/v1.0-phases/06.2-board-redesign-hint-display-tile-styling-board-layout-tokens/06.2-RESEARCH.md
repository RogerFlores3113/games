# Phase 06.2: Board Redesign - Research

**Researched:** 2026-09-17
**Domain:** Brownfield React/Tailwind visual rework of a working Hanabi table + one new server-authoritative action (shared discard order)
**Confidence:** HIGH for server-side (`reorderDiscard` has a direct, complete precedent) / MEDIUM for the client visual rework (no code precedent exists for hint tinting, wooden CSS texture, or fanned stacks — this is original design work) / MEDIUM-LOW for the 1280x720 fit budget (depends on content that varies by variant/discard count, not just fixed constants)

## Summary

This phase touches almost no new libraries — everything ships with existing tools (Tailwind v4 tokens, inline SVG per `suit-visuals.ts`, `safe-storage.ts`, the `reorder` action precedent). The work is almost entirely: (1) replacing `MarksZone`/`CandidateStrip`'s pip rows with a new hint-indicator system that tints the tile face and stamps a numeral on the tile back, (2) reworking `Table.tsx`'s layout from a horizontal flex-wrap of stat groups into a two-column composite (Play/Deck/Discard stacked vertically on the left, a vertical token line on the right), (3) a wooden-texture CSS treatment behind the existing city-at-night background, (4) an always-visible autosaving note box replacing `NoteChip`'s click-to-reveal pencil icon, (5) a drag shift-aside animation on top of the existing `useHandDrag`/`hanabi-drag-logic.ts` machinery, and (6) one new server action, `reorderDiscard`, built by copying the `reorder` action's five-file change set (`actions.ts`, `legality.ts`, `state.ts`, `projection.ts`, the client's `HanabiActionRequest` union) almost verbatim.

**Primary recommendation:** Treat this as two independent workstreams that only share `Table.tsx`/`toHanabiPlayerView`/`HanabiViewSchema`: (A) the server-side shared discard order, which is a mechanical copy of the `reorder` precedent and should be planned/executed first since it is fully specified and low-risk; and (B) the client visual rework, which is genuinely new design work with a real risk of breaking the UI-11 1280x720 no-scroll fit, and should be planned with an explicit height budget as a first-class task, not discovered during implementation.

### Pattern 1: Hint indicator as a client-only derived overlay, not a new wire field
**What:** HINT-01/02/03/04 need zero new fields on `HanabiView`. Everything needed to render a hint already exists in `card.facts.positiveClues` (an array of `{type: "color"|"rank", value}`) — the same data `CandidateStrip`'s `positiveMarks` already derives (see `hanabi-visual-logic.ts:candidateDisplayFor`). "Keep hints visible" (D-05) is a pure client display-persistence rule layered on top of the existing `positiveClues` array, which itself already accumulates and never resets except by consuming clues (server-side `clue-facts.ts` — verify it does not prune positiveClues; if it does, "keep hints visible" as specified needs the raw history, not just current facts, unless a card's positiveClues genuinely persist for its lifetime already, which the existing MarksZone/CandidateStrip pip persistence proves is the case since `NOTE-01`/`UI-04` already requires persistence "until the card leaves the hand or gains further information").

**When to use:** Any indicator whose truth is entirely a function of `card.facts` for the viewer's own hand, or `card.facts` + `card.suit/rank` for a teammate's hand (both already delivered).

**Example:**
```typescript
// Source: derived from hanabi-visual-logic.ts:candidateDisplayFor (existing pattern)
// hanabi-hint-logic.ts (NEW) — own-hand-safe: only reads CardFacts, never suit/rank.
export type HintDisplay = {
  colorHints: Suit[];   // every distinct color positively clued (D-06: hints stack)
  numberHints: Rank[];  // every distinct rank positively clued
};

export function hintDisplayFor(facts: CardFacts): HintDisplay {
  const colorHints = new Set<Suit>();
  const numberHints = new Set<Rank>();
  for (const clue of facts.positiveClues) {
    if (clue.type === "color") colorHints.add(clue.value as Suit);
    else numberHints.add(clue.value as Rank);
  }
  return { colorHints: Array.from(colorHints), numberHints: Array.from(numberHints) };
}
```
Rendering then applies `colorHints[0]`'s `--color-suit-*` as a tint (D-02) plus a non-colour marker (D-04 — reuse the suit's own `SuitGlyph` silhouette faintly, since that silhouette is ALREADY the colourblind-safe carrier the rest of the app uses for suit identity) and stamps `numberHints[0]` on the `FireworkCardBack` (D-03). D-06 says multiple hints stack — e.g. tinted AND numbered simultaneously — so the two are independent visual channels applied together, not mutually exclusive.

### Pattern 2: The `reorder` → `reorderDiscard` action, field-by-field mapping
**What:** DISC-01's entire server-side surface is a mechanical copy of the existing `reorder` action (own-hand reorder from 06.1-01), substituting `state.discardOrder` for `hand.slots` ordering. Concretely:

| File | `reorder` (existing) | `reorderDiscard` (new) |
|------|----------------------|--------------------------|
| `state.ts` | `HanabiAction` variant `{type:"reorder", cardIds}`; reorder acts on `hand.slots` (no new state field — order IS the array order) | Needs a NEW state field: `discardOrder: readonly string[]` (D-23/D-28) since `state.discard` is a flat array with no inherent "current arrangement" separate from insertion order. Add `HanabiAction` variant `{type:"reorderDiscard", cardIds}`. Add `HanabiView.discardOrder: string[]` |
| `actions.ts` | `isReorderRequest` (exact-key guard: `type`,`cardIds`) | `isReorderDiscardRequest`, IDENTICAL shape/guard logic, different literal type string |
| `actions.ts` | `applyReorder`: validates via `canReorder`, remaps `hand.slots` to the supplied id order, returns full state literal (no spread) | `applyReorderDiscard`: validates via `canReorderDiscard` (permutation against `state.discard.map(c=>c.id)`, NOT against a hand), sets `discardOrder: cardIds`, returns full state literal — must include the NEW `discardOrder` field in EVERY state-literal return site across `actions.ts` (every other action branch — play/discard/clue — also needs to carry `discardOrder` forward unchanged, since state literals are field-by-field, never spread) |
| `legality.ts` | `canReorder`: game-over gate only (deliberately no `isActorsTurn` — D-17); permutation check against the ACTOR's own hand ids | `canReorderDiscard`: same game-over-only gate (D-25: legal anytime, any seated player, not just the acting player's own resource) — but the permutation check is against `state.discard`'s ids, and there is NO "does this seat own these cards" check at all, since discard is shared. Also must independently verify the actor IS a seated player (`state.seatIds.includes(actorSeatId)`), since unlike hand reorder there's no natural "hand not found" guard to fall back on |
| `projection.ts` | N/A (hand order is visible structurally, not a separate field) | `discardOrder` computed ONCE in the shared "public fields" section at the top of `toHanabiPlayerView` (D-28) and included verbatim in BOTH the fail-closed unseated branch's return literal AND the seated branch's return literal — this is the exact bug shape the scout flagged: if it's computed twice, or in only one branch, per-seat divergence follows |
| `packages/schema/hanabi.ts` | N/A | `HanabiViewSchema` gains `discardOrder: z.array(z.string().min(1))` as a new required field in the top-level `z.strictObject` |
| `apps/web/components/hanabi/HanabiBoard.tsx` | `HanabiActionRequest` union has `{type:"reorder", cardIds}` | Add `{type:"reorderDiscard", cardIds: string[]}` to the same union |
| Client dispatch | `requestForDrop`/`hanabi-drag-logic.ts` reorder branch | A NEW pure module (e.g. `hanabi-discard-drag-logic.ts`) mirroring the reorder branch's shape but resolving drops within the discard pile/overlay rather than the hand — dispatches through the SAME `act()` chokepoint in `HanabiBoard.tsx` (D-27: last-write-wins, no client-side locking) |

**D-26/D-27 stale-submission handling:** exactly like `reorder`'s `applyPendingOrder` (client-side optimistic order in `hanabi-drag-logic.ts:applyPendingOrder`), a `reorderDiscard` UI should apply an optimistic client order with a timeout fallback (`PENDING_ORDER_TIMEOUT_MS` pattern from `useHandDrag.ts`) and let a stale server rejection (a discard landed mid-drag, changing the permutation set) silently revert to the server's `discardOrder` on the next frame — `canReorderDiscard`'s permutation check naturally rejects a submission that no longer matches the current discard set, satisfying D-26 without new logic.

**Anti-Patterns to Avoid:**
- **Storing discard order as a client preference (like notes/tile-colour):** D-23 explicitly forbids this — it must be shared server state, or players see different arrangements, defeating the point.
- **Spreading `state` in any new `reorderDiscard`-touching state literal:** every existing action branch in `actions.ts` already writes full field-by-field literals (HIDE-05/D-12 discipline); adding `discardOrder` means EVERY branch (`applyPlay`, `applyDiscard`, `applyClue`, `applyReorder`, and the new `applyReorderDiscard`) must be updated to carry the field forward, or `tsc` will catch the missing field (good) — but a spread "fix" to silence that error would violate the file's own documented discipline and must not be used.
- **Computing `discardOrder` per-branch in `projection.ts`:** must be computed once, in the shared section (per D-28), not duplicated in the seated/unseated branches.
- **Vertically stacking clue/fuse tokens without bounding the column to the Play/Deck/Discard column's height:** see Pitfall 1 below — this is the single biggest new layout risk in the phase.
- **Rendering the whole played stack by increasing each stack's flow height:** fan/step them so the ROW height stays roughly what a single card already costs (see Pitfall 1).

## Common Pitfalls

### Pitfall 1: The 1280x720 no-scroll fit (UI-11) — this phase both frees and spends height, and the ledger is not currently written down anywhere
**What goes wrong:** `HanabiBoard.tsx`'s `main` is `overflow-y-auto`, so a height overrun degrades silently into a scrollbar rather than a hard failure — the existing e2e assertions (`start-game.spec.ts` around line 390-397) check specific testids `toBeInViewport()` at 1280x720, which WILL fail if the budget is blown, but nothing catches an overrun until that specific test runs.

**Why it happens — the actual ledger, not guesswork:**
- **Freed by this phase:** `MarksZone`'s fixed 28px pip band is removed for BOTH own-hand (`ZONE_WIDTH.own`) and teammate cards (per HINT-04, "the automatic clue-mark pip rows... are removed"). That is 28px of vertical space freed per hand row, twice (teammates band AND own band) — this is a net height WIN, not a cost, contrary to the intuitive assumption that "adding features costs height."
- **Roughly free:** the always-visible note box (NOTE-03) replaces the note-chip row that already existed at a fixed 20px height (`MarksZone`'s own-only note-row) — going from click-to-reveal to always-visible doesn't need a taller box, just a different default state.
- **Roughly free:** wooden board texture, hint tint/numeral, token art redesign (SVG discs replacing the current 8px dot rows) — these are decorative/replacement, not additive, IF the token art's bounding box is kept comparable to the current 8px dots. A "black disc with a question mark" rendered at, say, 20-24px diameter is larger than the current 8px dot, so this is a real (small) per-token size increase.
- **The two real risks, both from BOARD-02 and BOARD-05:**
  1. **Vertical token line (BOARD-02):** the owner wants clue tokens "visible as a line of tokens going top->bottom," with up to 8 clue + 3 fuse tokens = 11 tokens in one vertical run. At even a modest 20px pitch (token + gap), that's ~220px of pure vertical space — far more than the ~89px the current horizontal clue/fuse row block costs. If this column is placed as ONE independent vertical block inside a page layout that is otherwise governed by horizontal row heights, it WILL blow the budget. **Mitigation:** the token column's height must be bounded by (not additive to) the height of the Play+Deck+Discard column it sits beside — i.e., the board becomes a `flex-row` with two children (stat column, token column) whose HEIGHTS ARE EQUAL because they are siblings in a flex row with `items-stretch`, not two independently-sized blocks stacked into the page's total height budget. Concretely: `<div className="flex ...">` with a left child (Play/Deck/Discard, likely 250-350px tall depending on fanned-stack height) and a right child (the 11-token column) — the right column's 11 tokens must be sized/spaced to fit WITHIN that same height (e.g., ~20-25px available per token slot if the left column is ~250px tall), not rendered at a fixed comfortable size that then forces the left column to grow to match.
  2. **Fanned/stepped played stacks (BOARD-05):** showing every card in a stack "clearly" (not just the top) is the single biggest open-ended height risk in the phase. A naive vertical fan of up to 5 cards per stack, times 5-6 suits, could easily add 150-250px if done vertically. **Mitigation:** fan HORIZONTALLY (cards overlap left-to-right within the existing ~64px-tall stack box, each card peeking out by ~15-20px) so the stack's flow HEIGHT stays what it is today (~64px) and only its WIDTH grows — width is the cheaper axis here since the play area already wraps (`flex-wrap`) and the page is 1280px wide with room to spare, while height is the tight axis (720px total, already shared across three bands).
- **No single source of truth exists today.** The scout's own flag stands: `gap-[3px]`, `py-[3px]`, the `28/20/16/48/64px` constants, and `min-h-0 flex-1` on the Table wrapper are scattered across `Table.tsx`, `HanabiBoard.tsx`, `Hand.tsx`, `OwnHandCard.tsx`, `TeammateCard.tsx`, and `MarksZone.tsx` with no shared constants file. This phase both removes constants (28px marks band) and adds new ones (token pitch, fan overlap, wooden-texture padding if any) — the plan MUST introduce a single explicit height-budget comment or constants module (even just a code comment enumerating "teammates band ≈ Npx + own band ≈ Mpx + table ≈ Kpx ≤ ~650px usable after chrome" at plan time) rather than discovering the total only when the 1280x720 e2e assertions fail.

### Pitfall 3: `own-hand-source.test.ts`'s file list is a hand-maintained allowlist that silently stops covering a file if not updated
**What goes wrong:** the D-15 identity-boundary guard only scans the files listed in `own-hand-source.test.ts` (`OwnHandCard.tsx`, `CandidateStrip.tsx`, `MarksZone.tsx`, `NoteChip.tsx`, `useHandDrag.ts` today). **How to avoid:** Make "add every new own-hand-touching component's path to `own-hand-source.test.ts`" an explicit acceptance criterion on every task that creates such a file, not an afterthought. ### Pitfall 4: Transient highlight state must use refs, not effect cleanup, because `game` is a new object every frame — hint persistence has the SAME trap
**What goes wrong:** `HanabiBoard.tsx`'s existing `justCluedIds` highlight (CR-01/WR-01 comments) had to move its clear-timer into a ref specifically because `game` is a brand-new object on every server push (partysocket frame), so an effect keyed on `[game]` re-runs on every frame — if the clear-timer were the effect's OWN cleanup, any frame arriving inside the highlight window would cancel-and-restart it, either extending the highlight forever or (worse) clearing it early depending on timing.

**Why it happens:** the same trap applies directly to HINT-03's "keep hints visible" feature: if OFF, hints must clear "once the next player has acted" — this is naturally modeled as "clear when `game.history.length` advances past the hint-granting clue's index," which is exactly the `touchedCardIdsFromLatestClue`/`justCluedIds` pattern already in the file. If a new hint-accumulation effect is written keyed on `[game]` with its clear-timer as cleanup, it will reproduce the exact bug 06.1 already fixed once (CR-01).

**How to avoid:** Model "keep hints visible OFF" as a derived value (does the current `game.history` have any turns after the clue that granted this hint?), not as a `setTimeout`-based transient like `justCluedIds`. Unlike the clue-touch flash (which is genuinely time-based — 2000ms — and unrelated to turn progression), hint persistence is turn-based, so it should be computed synchronously from `game.history`/`game.activeSeatId` on every render, with NO timer and NO ref-based clear logic needed at all. This sidesteps the entire pitfall class rather than replicating the existing ref workaround. Only reach for the ref pattern if a plan genuinely needs a time-based (not turn-based) hint clear, which nothing in the owner's spec calls for.

### Pitfall 5: `HanabiViewSchema` is `z.strictObject` at every level — a forgotten field anywhere is a hard parse failure, not a silent drop
**What goes wrong:** adding `discardOrder` to `HanabiView` (rules engine type) without adding it to `HanabiViewSchema` (wire schema) means `HanabiViewSchema.safeParse(view.game)` in `HanabiBoard.tsx` will fail with `schemaMismatch`, and the board renders "This game couldn't be displayed" for EVERY player, not just a missing feature — this is the existing `WR-04` "present-but-invalid game" gate, and it fails closed dramatically (visible error, not silent degradation).

**Why it happens:** `z.strictObject` rejects unknown keys on the way IN, but here the risk is the opposite direction — a key present in the TypeScript type but absent from the Zod schema simply makes every parse of a real server payload fail, since `strictObject` requires ALL its own declared keys to validate, and the actual payload will have `discardOrder` (from the real server) that the OLD schema doesn't declare — z.strictObject rejects "unrecognized keys," so an old client schema encountering a new server field would itself fail parsing.

**How to avoid:** `packages/schema/src/games/hanabi.ts`'s `HanabiViewSchema` and `packages/rules/src/hanabi/state.ts`'s `HanabiView` type must be updated in the SAME commit/task, never sequenced across two separate tasks where one could land without the other (a mid-deploy mismatch between `apps/web`'s bundled schema and `apps/worker`'s emitted view would break every game in progress). This is the exact class of risk the game-registration.ts compile-time assignability check exists to catch — run `npx tsc -b apps/web packages/rules packages/schema apps/worker` as an explicit gate in the plan, not just at the end.

### The existing `reorder` action end-to-end (the pattern `reorderDiscard` copies almost verbatim)
```typescript
// Source: packages/rules/src/hanabi/legality.ts:98-128 (existing, read in full during this research)
export function canReorder(
  state: HanabiState,
  actorSeatId: string,
  cardIds: readonly string[],
): Legality {
  if (isGameOver(state)) return { legal: false, reason: "game_over" };
  const hand = state.hands.find((h) => h.seatId === actorSeatId);
  if (hand === undefined) return { legal: false, reason: "card_not_in_hand" };
  const currentIds = hand.slots.map((s) => s.card.id);
  if (cardIds.length !== currentIds.length) return { legal: false, reason: "card_not_in_hand" };
  const currentSet = new Set(currentIds);
  const suppliedSet = new Set(cardIds);
  if (currentSet.size !== suppliedSet.size) return { legal: false, reason: "card_not_in_hand" };
  for (const id of cardIds) {
    if (!currentSet.has(id)) return { legal: false, reason: "card_not_in_hand" };
  }
  return { legal: true };
}
```
`canReorderDiscard` is this function with `hand.slots.map(...)` replaced by `state.discard.map((c) => c.id)`, no per-seat "hand" lookup (any seated player may call it — D-25), and a `state.seatIds.includes(actorSeatId)` check standing in for the "hand === undefined" not-found branch.

### Pointer-drag pattern `reorderDiscard`'s UI reuses
```typescript
// Source: apps/web/lib/hanabi-drag-logic.ts:81-95, 111-137 (existing, read in full)
export function reorderedCardIds(
  handIds: readonly string[],
  draggedId: string,
  targetIndex: number,
): string[] {
  const currentIndex = handIds.indexOf(draggedId);
  if (currentIndex === -1) return [...handIds];
  const without = handIds.filter((id) => id !== draggedId);
  const clampedIndex = Math.max(0, Math.min(targetIndex, without.length));
  const result = without.slice();
  result.splice(clampedIndex, 0, draggedId);
  return result;
}

// confirmation helper — is the exact shape a discard-pile equivalent needs,
// with cards = current discard order and pendingIds = the in-flight drag result.
```
