# Phase 6.1: Table Polish (Firework Art, Notes, Drag, Audio) - Research

**Researched:** 2026-09-17
**Domain:** Client-side game-table polish (SVG art, drag-and-drop reordering, Web Audio synthesis, localStorage notes) layered on an already-shipped, wire-frozen-until-now Hanabi client/server split
**Confidence:** HIGH

## Summary

This phase adds no new runtime dependencies — every requirement (ART-01/02, NOTE-01/02, HAND-01/02/03, AUD-01) is achievable with native browser APIs (`pointerdown`/`pointermove`/`pointerup`, `localStorage`, Web Audio `AudioContext`/`OscillatorNode`/`GainNode`) plus the existing `apps/web` dependency set (`react`, `clsx`, `zustand`, `lucide-react`). The 06.1-UI-SPEC.md already confirms this and gates any future drag-library addition behind the full Package Legitimacy Gate.

The one genuinely load-bearing engineering risk is HAND-01/HAND-03: they are the first change to the wire-frozen Hanabi rules engine and wire schema since Phase 4. Two engine changes are required in `packages/rules/src/hanabi/actions.ts`: (1) a new `reorder` action branch that validates a client-submitted card-id permutation of the actor's own hand and reorders `hand.slots` without touching turn state, tokens, or history; (2) changing `drawCard`'s append-at-end behavior to insert-at-the-vacated-index for both `applyPlay` and `applyDiscard`. Both changes must go through the existing chokepoints: `parseHanabiRequest`/`isXRequest` exact-own-key guards, `applyHanabiAction`'s dispatch, the unchanged `toHanabiPlayerView` projection (no schema change needed — hand order is already carried implicitly by array position on the wire), and the three property-test suites (`conservation.property.test.ts`, `redaction.property.test.ts`, `termination.property.test.ts`) plus `hanabi-leak-check.ts`, all of which must be extended to cover reorder and slot-preserving draw, not bypassed.

**Primary recommendation:** Treat this phase as two nearly-independent workstreams that share one gate: (A) a client-only visual/audio/notes workstream with zero server risk, and (B) a small, surgical engine change (reorder action + insert-at-index draw) that must be planned with the same TDD rigor as Phase 3's rules engine work, because it is the first post-freeze wire-contract change in the project.

### Pattern 2: History-diff-driven audio cues (no catch-up)

**What:** A cue never plays from reading the current `view` snapshot — only from a `history` entry that is NEW relative to the last time the client observed `history`.

**When to use:** AUD-01's D-29 "no catch-up audio" requirement.

**Example:**
```typescript
// apps/web/lib/hanabi-audio-cues.ts (new, pure — mirrors hanabi-board-logic.ts's style)
import type { HistoryEntryView } from "@games/rules";

export type Cue = "clue" | "play" | "discard" | "fuse" | "stack-complete";

/**
 * Given the FULL history array from the previous view and the FULL history
 * array from the new view, returns the cues to play for entries that are
 * new since the previous view — NEVER for entries present on the very first
 * view a client receives (initial join / refresh / reconnect catch-up,
 * D-29). Callers must special-case "previous is null" (first view ever
 * seen) as "play nothing", not "diff against an empty array" — an empty
 * array would replay the entire game's history as a burst of sound on
 * first load.
 */
export function cuesForNewHistory(
  previousHistory: readonly HistoryEntryView[] | null,
  newHistory: readonly HistoryEntryView[],
): Cue[] {
  if (previousHistory === null) return []; // first view ever — no catch-up
  const newEntries = newHistory.slice(previousHistory.length);
  return newEntries.map(cueForEntry).filter((c): c is Cue => c !== null);
}

function cueForEntry(entry: HistoryEntryView): Cue | null {
  if (entry.type === "clue") return "clue";
  if (entry.type === "draw") return null; // draw is silent — the triggering play/discard already cued
  if (entry.type === "discard") return "discard";
  if (entry.type === "play") {
    if (!entry.success) return "fuse"; // D-24: misplay plays fuse cue, never the play cue
    // D-28: a completing play (stack reaches 5) plays ONLY the completion
    // sound — this requires the caller to also pass current `stacks` (or
    // derive completion from a preceding/following history entry); the
    // simplest correct approach is: cuesForNewHistory takes prevStacks/
    // newStacks alongside history and special-cases a play entry whose
    // suit's stack just reached topRank 5.
    return "play";
  }
  return null;
}
```
**Critical detail for D-28 (completion-only sound):** `HistoryEntryView`'s "play" branch does not itself carry "did this complete the stack" — that must be derived by comparing `stacks` before/after (same pattern `Table.tsx`'s existing `newlyCompletedStacks(prevStacks, game.stacks)` already implements for the visual flash). The audio-cue selector should take the same two `stacks` snapshots `Table.tsx` already tracks, reusing `newlyCompletedStacks` from `hanabi-visual-logic.ts` rather than re-deriving stack-completion detection a second way.

### Pattern 3: Slot-preserving draw (engine change)

**What:** `drawCard` currently appends (`[...hand.slots, newSlot]`). It must instead insert at the index the played/discarded card occupied.

**Example (target diff shape for `packages/rules/src/hanabi/actions.ts`):**
```typescript
// Capture the index BEFORE removal (removeFromHand currently uses .filter,
// which loses position information).
function findHandIndex(hands: readonly Hand[], seatId: string, cardId: string): number {
  const hand = hands.find((h) => h.seatId === seatId);
  if (hand === undefined) return -1;
  return hand.slots.findIndex((s) => s.card.id === cardId);
}

// drawCard's signature gains an insertAtIndex param; the append-vs-insert
// behavior is the ONLY change — final-round/deck-empty short-circuit is
// unchanged.
function drawCard(input: {
  config: ReturnType<typeof variantConfig>;
  seatId: string;
  hands: readonly Hand[];
  deck: readonly HanabiCard[];
  finalTurnsRemainingBeforeThisTurn: number | null;
  insertAtIndex: number; // NEW
}): { hands: Hand[]; deck: readonly HanabiCard[]; drawnCardId: string | null } {
  // ... unchanged short-circuit ...
  const nextHands = hands.map((hand) => {
    if (hand.seatId !== seatId) return hand;
    const newSlot: HandSlot = { card: drawnCard, facts: initialClueFacts(config) };
    const slots = hand.slots.slice();
    slots.splice(insertAtIndex, 0, newSlot); // insert, don't push
    return { seatId: hand.seatId, slots };
  });
  // ...
}
```
Both `applyPlay` and `applyDiscard` must capture `findHandIndex(state.hands, actorSeatId, cardId)` **before** calling `removeFromHand` (which removes by filter and loses index), then pass that captured index as `insertAtIndex`. If the deck is empty or the final round has started, `drawCard` still returns `drawnCardId: null` and no insertion happens (hand simply shrinks) — this path is unchanged.

### Pattern 4: New engine action through the existing exact-own-key guard discipline

**What:** Every existing action guard (`isPlayRequest`, `isDiscardRequest`, `isClueRequest`) accepts ONLY an object whose own keys are an exact, closed set. The new `reorder` action must follow the identical discipline, not a looser shape.

**Example:**
```typescript
// packages/rules/src/hanabi/actions.ts — new guard, same shape as the three existing ones
export function isReorderRequest(
  request: unknown,
): request is { type: "reorder"; cardIds: string[] } {
  if (typeof request !== "object" || request === null) return false;
  const keys = Object.keys(request);
  if (keys.length !== 2 || !keys.includes("type") || !keys.includes("cardIds")) return false;
  const r = request as { type: unknown; cardIds: unknown };
  if (r.type !== "reorder" || !Array.isArray(r.cardIds)) return false;
  return r.cardIds.every((id) => typeof id === "string");
}
```
```typescript
// packages/rules/src/hanabi/legality.ts — new predicate, same Legality return shape
// as canPlay/canDiscard/canClue. Deliberately NOT gated on isActorsTurn or
// isGameOver — D-17 explicitly allows reorder anytime, including off-turn
// and (arguably) after game end, since it spends no resource and changes no
// scored state.
export function canReorder(
  state: HanabiState,
  actorSeatId: string,
  cardIds: readonly string[],
): Legality {
  const hand = state.hands.find((h) => h.seatId === actorSeatId);
  if (hand === undefined) return { legal: false, reason: "card_not_in_hand" };
  const currentIds = hand.slots.map((s) => s.card.id);
  // Exact permutation check: same length, same multiset of ids. A partial
  // list, a duplicate id, or an id from another seat's hand must all be
  // rejected — this is the boundary that keeps a client from asserting a
  // hand shape the server didn't deal.
  if (cardIds.length !== currentIds.length) return { legal: false, reason: "card_not_in_hand" };
  const currentSet = new Set(currentIds);
  const suppliedSet = new Set(cardIds);
  if (currentSet.size !== suppliedSet.size) return { legal: false, reason: "card_not_in_hand" }; // dup id
  for (const id of cardIds) {
    if (!currentSet.has(id)) return { legal: false, reason: "card_not_in_hand" };
  }
  return { legal: true };
}
```
```typescript
// applyReorder — no turn advance, no token/fuse change, no draw, no
// history entry (see Open Question 1 below on whether to log it at all).
function applyReorder(
  state: HanabiState,
  actorSeatId: string,
  cardIds: readonly string[],
): AdapterResult<HanabiState> {
  const legality = canReorder(state, actorSeatId, cardIds);
  if (!legality.legal) return { ok: false, error: legality.reason };

  const hand = state.hands.find((h) => h.seatId === actorSeatId)!;
  const slotsById = new Map(hand.slots.map((s) => [s.card.id, s]));
  const reorderedSlots = cardIds.map((id) => slotsById.get(id)!);

  const hands = state.hands.map((h) =>
    h.seatId === actorSeatId ? { seatId: h.seatId, slots: reorderedSlots } : h,
  );

  return {
    ok: true,
    state: {
      variant: state.variant,
      seatIds: state.seatIds,
      turnIndex: state.turnIndex, // UNCHANGED — reorder consumes no turn
      hands,
      deck: state.deck,
      stacks: state.stacks,
      discard: state.discard,
      clueTokens: state.clueTokens, // UNCHANGED
      fuses: state.fuses, // UNCHANGED
      finalTurnsRemaining: state.finalTurnsRemaining, // UNCHANGED
      history: state.history, // UNCHANGED unless Open Question 1 resolves to "log it"
    },
  };
}
```
`HanabiAction` in `state.ts` gains a fourth union member: `| { readonly type: "reorder"; readonly cardIds: readonly string[] }`. `applyHanabiAction`'s dispatch gains one more branch. No `packages/schema` change is required for the action request itself, because `GameActionMessageSchema.request` is `z.unknown()` at the room-protocol level (Hanabi-specific validation happens entirely inside `packages/rules`, per the existing pattern for play/discard/clue).

### Anti-Patterns to Avoid

- **Client-side hand reordering that isn't reconciled to the server:** Rendering the dragged order locally and never correcting it to match the next `state` push would silently desync from other players' view (breaking HAND-01's "every player sees the new order, including after a refresh" requirement) and could resurrect a stale visual order across a refresh. Always render `view.yourHand` array order as the truth; local drag state is presentation-only during the gesture, discarded the instant the drop resolves.
- **Using `Array.prototype.sort` or any client-side reordering of `otherHands`/`yourHand` for "nicer" display:** Per D-22, order IS information now — this project must never introduce a client-side sort, or hand order stops being meaningful.
- **Playing audio cues by diffing `view` snapshots instead of `history`:** A `view`-diff approach (e.g. "clueTokens went down, so play the clue sound") cannot distinguish a live action from a reconnect catch-up view, and is exactly the trap D-29 exists to prevent. Cues must be derived from `history` array growth, with the very first view's history explicitly excluded from cue generation.
- **Spreading `HanabiState` or `Hand` objects in the new `reorder`/`drawCard` code:** `actions.ts`'s file header explicitly forbids object-spread in this file (`{ ...state, hands }` is banned); every new/modified return value must be a named field-by-field literal, matching the discipline already used by `applyPlay`/`applyDiscard`/`applyClue`.
- **Building the note-chip storage key without defensive `try/catch`:** `localStorage` can throw (private browsing, storage quota exceeded, disabled by policy) — D-02 explicitly requires the feature to degrade to "notes don't persist" rather than crash the board. Wrap every `localStorage.getItem`/`setItem`/`removeItem` call.
- **Treating `AudioContext` creation as safe to do eagerly on mount:** Browsers block `audioContext.resume()`/creation-before-gesture under autoplay policy; D-26 requires deferring context creation/resume until the first user interaction anywhere on the page (a global `pointerdown`/`keydown` listener that fires once).

## Common Pitfalls

### Pitfall 1: `removeFromHand`'s `.filter()` loses the vacated index before `drawCard` needs it

**What goes wrong:** `removeFromHand` (existing code) removes a card by `hand.slots.filter((s) => s.card.id !== cardId)`, which produces a new array with no record of where the removed card was. If `drawCard` is modified to take an `insertAtIndex` but that index is computed AFTER calling `removeFromHand`, it will be computed against the already-shortened array, silently shifting the insertion point by one for every slot after the removed one.
**Why it happens:** The natural refactor path is "call the existing functions in the existing order, then figure out the index" — but the index must be captured from the PRE-removal hand.
**How to avoid:** Compute `findHandIndex(state.hands, actorSeatId, cardId)` (or equivalent) from `state.hands` — the hand as it existed before this action — immediately after legality passes, before calling `removeFromHand`. Pass that captured index straight through to `drawCard`.
**Warning signs:** A unit test that discards a card at index 0 of a 2-card hand and expects the draw to land at index 0 will instead show it landing at index -1/undefined-behavior or index 1 if this ordering bug is present — write that exact test first (index 0 removal on a >1-card hand) since it's the case most likely to silently pass a naive "draw replaces some slot" test but fail a "draw replaces THIS slot" test.

### Pitfall 2: Extending only `redaction.property.test.ts` and missing `conservation.property.test.ts`'s implicit hand-order assumptions

**What goes wrong:** `conservation.property.test.ts` and `termination.property.test.ts` were written before a `reorder` action existed. If their fast-check arbitraries generate action sequences from a closed `{play, discard, clue}` set, adding `reorder` to `HanabiAction` without also adding it to those arbitraries means the new action type is never exercised by the property suites at all — false confidence, not a caught regression.
**Why it happens:** Property-test arbitraries enumerate action types explicitly; a new union member requires an explicit arbitrary-generator update, which is easy to forget since TypeScript won't error (the arbitrary can still produce valid `HanabiAction` values without ever generating a `reorder`).
**How to avoid:** Grep `packages/rules/src/hanabi/*.property.test.ts` for wherever the action-type arbitrary is defined (likely a `fc.oneof(...)` or similar) and explicitly add a `reorder` generator case to each of the three property-test files, not just the one most obviously related to the change (redaction). Conservation must confirm reorder doesn't change deck/hand/discard card counts; termination must confirm reorder doesn't advance `turnIndex` or perturb `finalTurnsRemaining`.
**Warning signs:** Property tests pass immediately with zero changes needed to their assertions after adding the new action — a signal the arbitrary never generated the new action type in the first place, since a naive early draft of `applyReorder` that forgot to preserve `facts` correctly, for instance, would otherwise be caught.

### Pitfall 3: `own-hand-source.test.ts`'s structural source scan breaks (or silently stops enforcing) when `CandidateStrip` relocates

**What goes wrong:** `own-hand-source.test.ts` currently scans `OwnHandCard.tsx` and `CandidateStrip.tsx` by hardcoded file path and function-body extraction (`ownHandFunctionBody` looks for `"export function OwnHand("` inside `Hand.tsx`). If `MarksZone.tsx` becomes the new home for clue marks (per the UI-SPEC's relocation) and `CandidateStrip` is composed inside it rather than directly inside `OwnHandCard`, the D-15 identity-boundary test suite needs its scanned-file set updated to include `MarksZone.tsx` and `NoteChip.tsx` — otherwise the new files are never scanned for suit/rank property access at all, silently narrowing the safety net this test exists to provide.
**Why it happens:** The test's file list is a fixed set of paths, not a dynamic scan of "every file that renders inside OwnHand" — adding a new component in that render tree doesn't automatically get covered.
**How to avoid:** When `MarksZone.tsx`/`NoteChip.tsx` are created, extend `own-hand-source.test.ts`'s scanned-file list (and the equivalent check for `TeammateCard`'s marks-zone composition if one exists) to include them, applying the same `PROPERTY_ACCESS`/`DESTRUCTURING`/`FORBIDDEN_TOKENS` checks. Treat this as a required task, not an incidental side effect of the component split.
**Warning signs:** A note chip or marks-zone component that reads `card.suit`/`card.rank` (e.g. to conditionally style based on identity, which nothing in this phase should ever need to do) would compile and run fine, and only the source-scan test would have caught it — if that test isn't extended, nothing catches it.

### Pitfall 4: Audio cue for a misplay plays both "fuse" and "play" if the selector isn't careful about D-24/D-28 precedence

**What goes wrong:** A naive `if (entry.type === "play") return "play"` followed by a separate `if (!entry.success) return "fuse"` check (in the wrong order, or as two independent effects rather than one mutually-exclusive selection) could fire both cues for one action, violating D-24's explicit "misplay plays the fuse cue, not the play cue" (never both) and D-28's "completion-only, not play-then-completion" (never both).
**Why it happens:** It's natural to model "is this a play" and "did it complete a stack" and "did it succeed" as three independent boolean checks that each independently trigger a sound, rather than as one selection returning exactly one cue.
**How to avoid:** Model cue selection as a single function returning exactly one `Cue` (or `null`) per history entry — see Pattern 2's `cueForEntry` — with an explicit precedence: fuse (misplay) > stack-completion > plain play. Unit-test all three branches from one `play` history entry type (successful-non-completing, successful-completing, unsuccessful) to lock in mutual exclusivity.
**Warning signs:** A Playwright test that misplays a card and asserts exactly one `AudioContext` node was started (via a test-only hook or a mocked `AudioContext`) would catch a double-fire; a manual owner sign-off listening for "two sounds at once on a misplay" is the D-31 gate's actual catch mechanism if this slips through automated tests.

### Pitfall 5: Marks-zone height budget doesn't actually fit once notes are added, only verified for clue marks alone

**What goes wrong:** The UI-SPEC fixes the marks zone at a constant 28px regardless of content, and explicitly flags: "the executor must re-verify the no-scroll fit at 1280×720 once the zone is added." If the note chip's 44×44px invisible touch-target padding is implemented naively (e.g. actually reserving 44px of visible layout space instead of an invisible larger hit-area over a small visible glyph), the 28px zone will visually overflow for own-hand cards that have both clue marks and a populated note chip side by side.
**Why it happens:** "44px minimum touch target" and "28px zone height" read as two independent constraints, but they compose: a 44px-tall clickable element cannot fit inside a 28px-tall visual band unless the extra 16px of hit-area is achieved via `padding`/absolute-positioning tricks that don't consume layout height (e.g. a pseudo-element or an oversized invisible `::before`, not `min-height: 44px` on the visible button itself).
**How to avoid:** Follow the UI-SPEC's own stated precedent exactly ("matching the existing pattern of small glyphs inside larger touch-target buttons already used by OwnHandCard/TeammateCard") — inspect how the existing 06-03 card components achieve a 44px `min-height`/`min-width` touch target on visually smaller elements (likely via `style.minHeight`/`minWidth` on a `<button>` whose visible content is smaller, which does NOT grow the button's layout footprint beyond its content unless the parent flow forces it) before assuming the same trick works unchanged inside a fixed 28px flex row. Re-run the 1280×720 no-scroll Playwright check (06-06's existing viewport test) after adding the note chip, not just after adding clue marks alone.
**Warning signs:** A 5-player game with every own-hand card carrying both clue marks and a note produces a page that requires scrolling at 1280×720 — this is exactly the class of regression Phase 6's own D-06 tightening (06-06's SUMMARY) had to fix once already for candidate strips; treat the marks-zone height budget with the same suspicion.

## Code Examples

### Web Audio short envelope tone (D-24/D-25)

```typescript
// apps/web/lib/hanabi-audio-synth.ts (new)
// [ASSUMED: standard Web Audio API usage pattern, not verified against a
// specific spec/MDN revision this session — this is stable, long-established
// browser-platform knowledge, not library-specific documentation]

let sharedContext: AudioContext | null = null;

/** Creates (once) or returns the shared AudioContext. Must only be called
 * from inside a user-gesture event handler the first time, per browser
 * autoplay policy (D-26) — call this from a one-time global pointerdown/
 * keydown listener installed on mount, not eagerly on component mount. */
export function getAudioContext(): AudioContext {
  if (sharedContext === null) {
    sharedContext = new AudioContext();
  }
  if (sharedContext.state === "suspended") {
    void sharedContext.resume();
  }
  return sharedContext;
}

export interface ToneSpec {
  frequency: number;
  durationMs: number;
  type: OscillatorType; // "sine" | "triangle" for a soft, non-buzzy character (D-24)
}

/** Plays a single short tone with a linear attack/decay envelope (avoids the
 * audible click of starting/stopping an oscillator at full gain). `volume`
 * is 0..1, applied as the envelope's peak gain. */
export function playTone(spec: ToneSpec, volume: number): void {
  if (volume <= 0) return;
  const ctx = getAudioContext();
  const osc = ctx.createOscillator();
  const gain = ctx.createGain();
  osc.type = spec.type;
  osc.frequency.value = spec.frequency;

  const now = ctx.currentTime;
  const attackEnd = now + 0.01;
  const releaseEnd = now + spec.durationMs / 1000;

  gain.gain.setValueAtTime(0, now);
  gain.gain.linearRampToValueAtTime(volume, attackEnd);
  gain.gain.exponentialRampToValueAtTime(0.001, releaseEnd);

  osc.connect(gain).connect(ctx.destination);
  osc.start(now);
  osc.stop(releaseEnd + 0.02);
}
```

### Defensive localStorage wrapper (D-02, note persistence)

```typescript
// apps/web/lib/hanabi-notes.ts (new)
// Mirrors apps/web/lib/seat-token.ts's established defensive localStorage
// pattern for this codebase (not a new convention).

function noteKey(roomCode: string, seatId: string, cardId: string): string {
  return `hanabi-note:${roomCode}:${seatId}:${cardId}`;
}

export function readNote(roomCode: string, seatId: string, cardId: string): string {
  try {
    return window.localStorage.getItem(noteKey(roomCode, seatId, cardId)) ?? "";
  } catch {
    return ""; // D-02: storage access can throw (private mode, quota, policy) — degrade silently
  }
}

export function writeNote(roomCode: string, seatId: string, cardId: string, text: string): void {
  const trimmed = text.slice(0, 20); // D-06: ~20 char cap enforced here too, not only via maxLength
  try {
    if (trimmed === "") {
      window.localStorage.removeItem(noteKey(roomCode, seatId, cardId));
    } else {
      window.localStorage.setItem(noteKey(roomCode, seatId, cardId), trimmed);
    }
  } catch {
    // D-02: a full/disabled localStorage must not crash the board.
  }
}

/** Called when a card leaves the own hand (played/discarded) — D-04. */
export function deleteNote(roomCode: string, seatId: string, cardId: string): void {
  try {
    window.localStorage.removeItem(noteKey(roomCode, seatId, cardId));
  } catch {
    // same defensive degrade
  }
}
```
**Lifecycle wiring note:** "when the card leaves the hand its note is deleted" (D-04) requires the client to detect a card-id disappearing from `view.yourHand` between one `state` push and the next (a diff, similar in shape to the audio-cue history diff) and call `deleteNote` for every id that was present before and is absent now. This is a second, independent diff (over `yourHand` card ids, not `history`), not reusable from the audio-cue diff logic, but should follow the same "pure diff function in `lib/`, thin effect in the component" pattern.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A client submits a `reorder` `cardIds` array that is not a true permutation of their current hand (missing id, duplicate id, or an id belonging to another seat's hand), attempting to corrupt server state or desync client views | Tampering | `canReorder`'s exact-set-membership + length check (Pattern 4) rejects any non-permutation before `applyReorder` ever touches `hand.slots`; this mirrors the project's existing "exact-own-key" discipline used throughout `actions.ts` for play/discard/clue payloads |
| A client submits a `reorder` action targeting a game state where the actor is not currently seated (stale/forged seat association) | Spoofing | Unchanged from the existing pattern — `actorSeatId` is derived server-side from the authenticated WebSocket connection's bound seat (RoomDO's existing seat-binding machinery), never trusted from the request payload itself; this is identical to how `play`/`discard`/`clue` already work and requires no new mechanism |
| A malicious or buggy client submits an oversized/malformed `cardIds` array (e.g. thousands of entries) as a denial-of-service attempt against the server's permutation-check loop | Denial of Service | The existing hand size is small (4-5 cards) and `canReorder`'s length check (`cardIds.length !== currentIds.length`) rejects any array whose length doesn't match the actual hand size in O(1) before the more expensive set-membership loop runs — no new DoS surface introduced beyond what any other action-payload validation already handles |
| `localStorage` note content is later mistakenly sent to the server (e.g. a future refactor accidentally wires the note chip's onChange into the WebSocket `send` path) | Information Disclosure (of player's private strategic notes, not game-secret data — but still a stated D-01 requirement) | D-01 is explicit: never send notes to the server. The recommended implementation (`hanabi-notes.ts` as a standalone module with no import of `room-socket.ts`/`send`) structurally keeps notes out of the wire path — the planner should ensure `NoteChip.tsx`'s only side effect is calling `writeNote`/`readNote`, never `onAction`/`send` |
