## Decisions Made

- Exercised **Black variant, 5 seats** as the worst case (not base) — the variant picker is already proven selectable end to end by an earlier plan's own test (`start-game.spec.ts`'s first test uses Black), so the plan's documented fallback ("if the variant is not selectable end-to-end yet, use base...") did not apply.
- The worst-case-driving loop treats a deep discard pile (>=8) and an advanced stack (rank >=3) as **soft targets it steers toward, not hard requirements** — it never risks the game's last fuse, and the fit/band assertions that follow do not depend on hitting either target exactly. This run reached a 30-tile discard pile (well past the 8-tile target) but a max stack rank of 0 (random single-slot plays didn't luck into an early rank-1 card this run) — the deep discard pile alone was enough to expose the real regression below.
- **No `layout-budget.ts` constant needed to change.** The regression this task's own measurement was designed to catch turned out to be a real component bug (see Deviations), not a wrong ledger number — fixing the component brought the measured bands back inside the existing 40px tolerance of `TEAMMATE_BAND_PX` (117 vs 140), `TABLE_BAND_MIN_PX + BOARD_CHROME_PX` (282 vs 276), and `OWN_BAND_PX` (309 vs 300).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Three buttons were unclickable by mouse in production**

- **Found during:** Task 1, writing the HINT-03 (`keep-hints-toggle`) and TILE-03 (`tile-color-picker-toggle`, swatch buttons) scenarios — Playwright's `.click()` timed out after 30s reporting the click was intercepted by a sibling `<span>`.
- **Issue:** `keep-hints-toggle`, `tile-color-picker-toggle`, and every `tile-color-swatch-*` button had their enlarged (44px) touch-target hit area implemented as an absolutely-positioned `<span>` placed as a DOM **sibling** immediately after the `<button>`, inside a shared wrapper. Painted after the button with no z-index difference, that sibling span sat on top of the button and covered its entire visible area, silently swallowing every mouse click at the button's own visual location — in a real browser, not just in Playwright. These three controls were, in effect, non-functional by mouse before this plan.
- **Fix:** Moved each overlay span to be a **descendant** of its button (its last child) instead of a sibling, matching `Table.tsx`'s `discard-toggle`, which used this pattern correctly and was the only one of the four that already worked. Kept the exact same inset values, so the touch-target size is unchanged.
- **Files modified:** `apps/web/components/hanabi/HanabiBoard.tsx`, `apps/web/components/hanabi/TileColorPicker.tsx`
- **Commit:** `3d1a919`

**2. [Rule 1 - Bug] The Black/Rainbow variant broke the 1280x720 no-scroll fit at 5 players**

- **Found during:** Task 3, the mandated worst-case measurement (5 seats, Black variant) — `document.scrollingElement.scrollHeight` (776px) exceeded `clientHeight` (720px).
- **Issue:** `CluePicker`'s value row renders one button per cluable colour (5 for base, 6 for Rainbow/Black). At 5 players and 1280px width, the extra 6th colour button widened that row enough to push the sibling `AudioControls`/keep-hints-toggle/tile-colour-picker group off the same wrapped line it used to share with `CluePicker`, adding an entire extra wrapped line (~108px) to the bottom controls row — measured 369px against the 300px `OWN_BAND_PX` budget, breaking the fit specifically for the two variants this phase's own box-variant requirement (Rainbow/Black) exists to support. Every earlier fit check in this phase (06.2-07's early check, the existing UI-11 test) used the base variant only, so this never surfaced before.
- **Fix:** Reordered `HanabiBoard.tsx`'s bottom-controls-row children so the `AudioControls`/toggles group sits **before** `CluePicker` instead of after it. `CluePicker` is the only element in that row whose width scales with the variant's suit count; moving it to be the row's last child means it always wraps onto its own line regardless of how many colour buttons it renders, instead of contending with a narrower sibling group for space on a shared line. Verified live: `scrollHeight` returned to exactly 720px (zero-slack, matching the pre-existing zero-slack fit for base variant), and the measured bottom-row height dropped from 369px to 309px — inside the existing 40px tolerance.
- **Files modified:** `apps/web/components/hanabi/HanabiBoard.tsx`
- **Commit:** `27406d9`
