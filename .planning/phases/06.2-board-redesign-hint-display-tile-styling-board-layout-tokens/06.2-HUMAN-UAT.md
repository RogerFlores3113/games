## Sign-off checklist prepared for the owner (from this phase's own testing and SUMMARYs)

### Two bugs found during this phase's own testing (fixed, for the record)

1. **Three controls were unclickable by mouse in production.** The keep-hints toggle, the tile-colour-picker toggle button, and every tile-colour swatch button had their enlarged (44px) touch-target hit area implemented as a sibling `<span>` painted after the button, which silently sat on top of the button and swallowed every mouse click — not just a Playwright artifact, a real production bug. Fixed by moving each overlay span to be a descendant (last child) of its button instead, matching the one control (`discard-toggle`) that already did this correctly. Commit `3d1a919`.
2. **The 6-colour Rainbow/Black variants broke the 1280x720 no-scroll fit.** `CluePicker`'s value row grows by one button per cluable colour (6 for Rainbow/Black vs 5 for base); at 5 players and 1280px width the extra button pushed the sibling audio/toggle controls onto their own extra wrapped line, breaking the fit specifically for the two box variants this phase exists to support. Fixed by reordering the bottom-controls-row children so `CluePicker` (the only element whose width scales with variant suit count) is always the row's last child, guaranteeing it wraps onto its own line regardless of suit count. Commit `27406d9`.

### The UI-11 fit regression and its real cause

The always-visible note box's input had no explicit width, so the browser gave it its intrinsic default text-input width (~200px) instead of the 88px tile width beneath it. That made the whole own-hand row render 862px wide instead of ~410px, which pushed the clue picker/card actions/audio controls onto extra wrapped lines purely by width, not by any real height need — 847px page height against a 720px viewport. Fixed by giving the note box's container and the per-card hand slot an explicit 88px width instead of `w-full` (commits `705b65a`, `7a092df`). The layout-budget ledger (`apps/web/lib/layout-budget.ts`) was corrected to the measured reality rather than left with numbers that only made an arithmetic-only test pass without reflecting the real render: `OWN_BAND_PX` 180 → 300, `BOARD_CHROME_PX` 40 → 16.

### A behaviour change the owner must decide on

The expanded discard-pile overlay no longer groups tiles by suit. A single shared, draggable discard order (any player can rearrange it, and everyone sees the same arrangement — DISC-01) cannot coexist with an automatic suit-grouped presentation, since the server only stores one order. The overlay now shows the shared arrangement only, with no suit grouping. **Ask the owner explicitly:** is a single shared order with no suit grouping acceptable, or do they want a "group by suit" action that re-sorts the shared order for everyone (a visible, shared re-sort, not a private view)?

### Worst case measured

5 seats, Black variant (6 cluable colours, the largest clue-picker row), a 30-tile discard pile, and advanced played stacks — 1280x720, no scrolling. Measured live: `teammates` band 117px, `tableau` 282px, bottom controls row 309px, page total exactly 720px (zero slack).
