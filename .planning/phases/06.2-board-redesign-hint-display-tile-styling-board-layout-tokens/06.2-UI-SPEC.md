|-------|-------|-------|

| sm | 8px | Note-box-to-tile gap, tile-colour swatch gaps |
| md | 16px | Default element spacing (unchanged) |
| lg | 24px | Section padding (Play/Discard area outline padding) |
| xl | 32px | Layout gaps (unchanged) |
| 2xl | 48px | Major section breaks (unused this phase) |
| 3xl | 64px | Page-level spacing (unused inside the fixed game view) |

Exceptions:
- `--size-touch-min: 44px` (inherited) — every clickable control, **including the keep-hints toggle, the tile-colour swatch buttons, and any discard-pile drag handle**, uses a 44×44px minimum click target via the project's established out-of-flow inset-span pattern (visible glyph stays small; the invisible hit area is 44px). - **Removed this phase (frees height, not a new exception):** the fixed 28px `MarksZone` pip band above every card (own-hand and teammate alike) is deleted per HINT-04. This is the single largest source of freed vertical space this phase spends elsewhere.

## Color

Palette: dark "fireworks night" (unchanged base, Phase 1 D-16). Most of this phase's visual need (hint tint, wooden texture, tile-colour palette) is satisfied by existing tokens or by tokens computed at render time via CSS functions (`color-mix`, opacity layering) from existing tokens. `globals.css`'s no-hex-outside-`@theme` rule is unconditional — its one prior exception (`.table-backdrop`'s scrim) is only an existing token's exact value at partial opacity, introducing no new colour, and is not a precedent for a genuinely new colour. This phase therefore **adds seven new named `@theme` tokens** (five tile-colour presets, one token-art disc/rim pair, one tile drop-shadow) — see the token table below — each documented in `globals.css`'s header in the same style as the existing `--color-accent`/scrim notes, explicitly scoped to decorative/token-art fills, never part of the accent/suit/destructive semantic set. `--color-accent` keeps its exact 7 documented uses; this phase adds **zero** new accent uses (the keep-hints toggle, tile-colour picker, and token art are deliberately styled with `--color-border`/`--color-text-muted`/`--color-card-glow`/`--color-suit-*`/the new tokens below, never accent, to avoid an 8th reserved use).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0F1A` (`--color-bg`, inherited) | Page background, under the city-at-night image + wooden-board layer |
| Secondary (30%) | `#141A2E` (`--color-surface`, inherited) | Board panel background (beneath the wooden texture overlay), tile base fill, note-box background |
| Accent (10%) | `#F5B942` (`--color-accent`, inherited) | **Unchanged — still exactly 7 uses.** Not extended this phase. |
| Destructive | `#F0453D` (`--color-destructive`, inherited) | Unchanged — fuse-lost flash only. Fuse **token art** itself is NOT destructive-red per the owner's literal description (black disc, yellow explosion, orange-red rim) — see Board Layout. |

**New `@theme` tokens this phase (named, documented, not literals):**

| Token | Value | Doc-comment purpose (added to `globals.css` header, `--color-accent`/scrim style) |
|---|---|---|
| `--color-tile-preset-warm-sand` | `#3A3220` | "Tile-colour preset — decorative personal-preference fill (TILE-03), not a suit/accent/destructive signal" |
| `--color-tile-preset-cool-teal` | `#1A3236` | Same purpose comment as above |
| `--color-tile-preset-plum` | `#2A1F35` | Same purpose comment as above |
| `--color-tile-preset-charcoal` | `#1C1F26` | Same purpose comment as above |
| `--color-token-disc` | `#000000` | "Token-art disc fill (clue/fuse tokens, BOARD-02) — near-black token-game art, not a semantic colour; reuses `--color-bg`'s near-black value in spirit but declared as its own token since token art must stay pure black regardless of any future `--color-bg` change" |
| `--color-token-fuse-rim` | `#E8722C` | "Fuse-token rim (BOARD-02) — orange-red token-art stroke per the owner's literal description, distinct from `--color-suit-yellow` and `--color-destructive`; token art only, never reused as a semantic signal" |
| `--color-tile-shadow` | `rgba(0, 0, 0, 0.4)` | "Tile drop-shadow (TILE-01) — an opacity-only rgba black, not a semantic colour, following the same 'derive from a fixed value, document why' discipline as the `.table-backdrop` scrim" |

The slate preset needs no new token — it stays `color-mix(in srgb, var(--color-surface) 100%, transparent)`, a derivation of an existing token, not a new colour. This is a **location change only**: which colour renders where is unchanged from the original draft; every value above is now a named `@theme` token instead of an inline literal, consumed the same way (`var(--color-tile-preset-warm-sand)`, etc.) wherever the sections below reference these fills.

**HINT-01 colour tint (D-02, D-04):** a colour clue tints the touched tile using that suit's own `--color-suit-*` hue, applied as a **translucent overlay wash across the tile face** (`background: color-mix(in srgb, var(--color-suit-{suit}) 22%, var(--color-surface))`, i.e. a 22%-strength tint of the suit hue mixed into the tile's base surface colour) — no new token, computed from the existing suit-hue token at render time. Per D-04, colour is never the sole carrier: the same tinted tile also shows the suit's own `SuitGlyph` silhouette (A3, RESEARCH.md) rendered faintly (`opacity: 0.35`) in one corner as the non-colour marker, reusing the exact silhouette that already carries suit identity everywhere else in the app, so a grayscale check still reveals which colour was clued by shape alone.

**HINT-02 number-clue numeral (D-03):** the touched number renders as a Label-role numeral on the tile back, in `--color-text` on a small `--color-surface` chip inset in a fixed corner of the tile back (opposite corner from the colour-hint's glyph marker, so the two can compose — D-06).

**D-06 composition (Claude's Discretion, owner reviews at sign-off):** a colour hint and a number hint on the same tile compose as **independent, non-overlapping visual channels** — colour tint spans the whole tile face; the suit-glyph marker sits in the top-left corner; the number-clue numeral sits in the bottom-right corner. Multiple colour clues (e.g. Rainbow touched by more than one colour name) or multiple number clues on the same tile are not possible under the rules (each is a single value), so no further stacking logic is needed beyond "colour occupies one channel, number occupies the other, both can be present at once."

**Wooden board texture (D-11, D-15):** CSS-only, layered `repeating-linear-gradient` grain lines at low opacity over a `linear-gradient` base, composed entirely from existing tokens via `color-mix`/rgba-of-`--color-surface` — e.g. a base of `color-mix(in srgb, var(--color-surface) 85%, #000 15%)` (a **derived**, not new, near-token value — same "derive from an existing token" discipline 06.1 used for its background scrim) with two `repeating-linear-gradient` grain layers at `4-8%` opacity for the plank/grain lines. This sits **on the board area only** (the tableau panel), not the page — the 06.1 city-at-night background stays behind it, visible through the board's own edges/gaps, per D-15. If the CSS result looks poor at review, fall back to a licensed wood texture image with a `CREDITS.md` entry, following 06.1's exact precedent (D-11 explicit fallback).

**Tile surface vs. board surface (TILE-01, D-12):** tiles get a **lighter, opaque, raised** surface distinct from the board beneath: `background: var(--color-surface)` (or the player's chosen tile colour, TILE-03) with a `border: 1px solid var(--color-border)` plus a small downward `box-shadow: 0 2px 4px var(--color-tile-shadow)` — the new `@theme` token from the table above (an "object resting on a surface" cue, not a luminosity signal — luminosity keeps using the existing frame-glow system, unchanged) — this reads as a tile sitting on the wooden board rather than a flat tinted rectangle.

**Tile-colour preset palette (TILE-03, D-13/D-14):** a small **fixed set of 5 presets**, each independently verified to keep ≥4.5:1 contrast against `--color-text`/`--color-text-muted` and to stay visually distinguishable from every `--color-suit-*` hue and from `--color-card-glow` (so a tinted-by-hint tile and a coloured-by-preference tile never read as the same signal):
| Preset name | Token | Note |
|---|---|---|
| Slate (default) | `color-mix(in srgb, var(--color-surface) 100%, transparent)` | Current/unchanged tile look — the default, zero-opt-in state; a derivation of an existing token, needs no new `@theme` entry |
| Warm sand | `var(--color-tile-preset-warm-sand)` | New `@theme` token (see table above) |
| Cool teal | `var(--color-tile-preset-cool-teal)` | New `@theme` token (see table above) |
| Plum | `var(--color-tile-preset-plum)` | New `@theme` token (see table above) |
| Charcoal | `var(--color-tile-preset-charcoal)` | New `@theme` token (see table above) |
All five are used only as tile-fill backgrounds, never as suit/hint/accent signal colours, so they do not compete with any existing token's reserved meaning — each is declared as its own named `@theme` token per the location-change fix above, not a literal.

**Clue token art (BOARD-02, D-18, D-20):** black disc (`fill: var(--color-token-disc)`, the new named token above — never a `#000` literal) with a centered blue question mark (`--color-suit-blue`, reusing the existing suit-hue token rather than a new blue literal).

**Fuse token art (BOARD-02, D-18, D-20):** black disc (`fill: var(--color-token-disc)`, same named token as the clue disc) with a centered yellow explosion (`--color-suit-yellow`) and an orange-red rim stroke — `stroke: var(--color-token-fuse-rim)`, the new named token above — since neither existing token matches "orange-red" and the owner's description is specific; scoped to token art only, never reused elsewhere.

**Accent reserved-for list (unchanged, still exactly 7 uses):** primary CTA fill ("New game" only), room-code Display text, own-seat "you" ring, active-turn hand-container ring/glow, own-hand "Your turn" state accent, focus rings on all interactive controls, note-chip focused/editing outline (06.1 D-02 extension). This phase adds none.

## Layout — Height Budget (the explicit ledger RESEARCH.md Pitfall 1 requires)

Extends Phase 6/6.1's fixed three-band desktop layout — the 1280×720 no-scroll target (UI-11) is a hard constraint this phase must re-verify, not assume. The board's primary visual focal point is unchanged by this redesign: the active player's hand-container ring/glow and turn indicator (Phase 6 Active-Player Indication, D-02) remain the single brightest, highest-contrast piece of chrome on screen — none of this phase's additions (hint tint, token column, wooden texture) compete with or relocate that priority.

**Freed by this phase:** the 28px `MarksZone` pip band is removed above every card, both bands.
**Spent by this phase:** the vertical token column, fanned played stacks, deck-counter repositioning, Play/Discard outlines+labels.

| Band | Current (06.1) | This phase | Delta | Why |
|------|----------------|-------------|-------|-----|
| Top (teammate hands) | 168px (seat label 20 + card row 78 + status row 20 + marks 28 + gaps/padding) | **140px** (seat label 20 + card row 78 + status row 20 + gaps/padding, marks band removed) | −28px | HINT-04 removes the pip band; teammates get no note box (own-hand only, D-09) |
| Bottom (own hand) | 208px (turn indicator 24 + card row 100 + controls row 44 + marks 28 + note-row 20 + gaps/padding) | **180px** (turn indicator 24 + card row 100 + controls row 44 + note-row 20 [now always-visible, same 20px budget], gaps/padding, marks band removed) | −28px | HINT-04 removes the pip band; NOTE-03's always-visible box reuses 06.1's existing 20px note-row budget rather than growing it |
| Center (tableau) | `flex-1`, ~304px available | `flex-1`, **~360px available** (304 + 56px freed from top/bottom) | +56px | Absorbs BOARD-01/02/04/05 below |

**Center band internal budget (new structure, `flex-row` with two children of equal, stretched height — the Pitfall 1 mitigation):**

```
┌───────────────────────────────────────────┬──────────────┐
│  LEFT COLUMN (Play / Deck / Discard)       │ RIGHT COLUMN │
│                                             │ (token line) │
│  Play area   ~100px (label 14 + fanned      │  ~11 tokens  │
│              stacks 64 + outline padding)   │  at equal    │
│  ───────────────────────────────────        │  height to   │
│  Deck counter ~48px (small FireworkCardBack │  the left    │
│              32×44 + "48 x" text, centered)  │  column, so  │
│  ───────────────────────────────────        │  pitch =     │
│  Discard area ~112px (label 14 + reorderable│  ~260px/11   │
│              tile row 64-88, outline padding)│  ≈ 20-24px   │
│                                             │  per token   │
│  TOTAL: ~260px                             │  TOTAL: ~260px│
└───────────────────────────────────────────┴──────────────┘
```

`items-stretch` on the shared `flex-row` parent makes the right column's height **exactly equal to** the left column's height, not independently sized — this is the direct fix for RESEARCH.md's flagged Pitfall 1 risk ("11 tokens at a comfortable 20px pitch costs ~220px if laid out independently"). The right column's per-token art (disc diameter) must fit **within** that height, computed as `(left-column-height − (token-count−1)×gap) / token-count`; if the left column's height changes (e.g. discard grows to two rows because a game has accumulated many discards), the right column's token size shrinks to match rather than growing the page. Never size the token column first and let the left column grow to match it.

**Fanned played stacks (BOARD-05, D-22) — fan horizontally, not vertically:** each stack's row height stays the existing single-card height (~64px); every card in the stack overlaps the previous one, peeking out by **16px** per additional card (so a complete 5-card stack spans `48 + 4×16 = 112px` wide instead of 5× the card height tall). This spends the cheap axis (page width, 1280px with room to spare) instead of the tight axis (height).

**Mandatory verification task:** run the app at 1280×720 with a 5-player Black or Rainbow game (6 suits, worst case for both the token column's fuse+clue count and the fanned-stack width) and confirm zero scrollbar via Playwright `toBeInViewport()` on every existing and newly-added testid, per RESEARCH.md's explicit recommendation. This is a first-class, separately-tracked task in the plan, not a side effect of the last visual task.

## Hint Display System (HINT-01..04)

Replaces `MarksZone`/`CandidateStrip`'s pip rows entirely (HINT-04) — no replacement for negative/ruled-out information is designed anywhere in this spec, per D-07 (owner-confirmed 2026-09-17, "Let it go"). Do not add a hover/click reveal for ruled-out information; the owner was shown that option and declined it.

- **Data source:** a pure derivation from `card.facts.positiveClues` alone (own-hand-safe — never reads `suit`/`rank`), computed synchronously on every render, **not** a `setTimeout`-based transient (RESEARCH.md Pitfall 4 — hint persistence is turn-based, not time-based, so it must never use the `justCluedIds`-style ref/timer pattern).
- **"Keep hints visible" toggle (HINT-03, D-05):** per-player, client-side, persisted via `safe-storage.ts` (never a second storage wrapper). Default **off**. When off, a hint clears once `game.history.length` has advanced past the index of the clue that granted it (derived synchronously from `game.history`/`game.activeSeatId`, never a timer). When on, a hint persists until the card leaves the hand. Toggle control lives in the bottom band's controls row (same row as Play/Discard/Give-clue, icon-only, 44px touch target, `Eye`/`EyeOff` lucide icon), `aria-label="Keep hints visible"` / `aria-label="Clear hints after each move"`.
- **Colour hint (HINT-01):** tile-face tint + faint non-colour suit-glyph marker, per Color § above.
- **Number hint (HINT-02):** numeral stamped on the tile back, per Color/Typography § above.
- **Composition (HINT-04, D-06):** colour and number hints are independent channels that can coexist on one tile, per Color § D-06 composition above.
- **Applies to:** own-hand tiles (via `facts` only — same D-15 identity boundary as everything else) and teammate tiles (via `facts` + the teammate's own already-visible suit/rank, matching Phase 6's existing "teammates see their own facts too" precedent).

## Hand Interaction

### Drag shift-aside (DRAG-01, D-08)

During a drag reorder, every other tile in the hand animates its position to open a gap at the current drop index — an extension of the existing `useHandDrag.ts`/`hanabi-drag-logic.ts` pointer-tracked `dragState`, not a new drag paradigm (RESEARCH.md "Don't Hand-Roll" — no HTML5 DnD, no drag library). Motion: `transform` transition on the non-dragged tiles (`transition: transform 150ms ease-out`, reusing the existing `.drag-snap` class's timing/easing from `globals.css`), paired with a `prefers-reduced-motion` static end-state (tiles jump directly to their shifted position with no animated transition, signal — the gap — still visible).

### Always-visible note box (NOTE-03, D-09/D-10)

Replaces `NoteChip.tsx`'s click-to-reveal pencil icon. A **20px-tall** box sits directly above each own-hand tile (reusing 06.1's existing note-row budget, per the Height Budget table above), with:
- **Resting state:** barely-visible `--color-border` outline (1px), transparent/`--color-surface`-at-low-opacity fill, no placeholder text shown unless focused.
- **Hover state:** outline brightens slightly toward `--color-text-muted` (a discoverability cue that this is clickable), no layout shift.
- **Focus/editing state:** `--color-accent` outline (reuses the existing reserved "focus rings on interactive controls" use, same as 06.1's `NoteChip` focus state — not an 8th accent use), placeholder text `"Note…"` shown only while empty and focused.
- **Autosave:** debounced write to `hanabi-notes.ts` storage on every change (not only on Enter/blur) — per D-09, the box is always live, so autosave must not wait for an explicit commit gesture.
- **Character cap:** reconsidered from 06.1's 20-character chip cap since the box is now always visible and inviting longer text — set to **40 characters**, sized to the tile's width without truncation/ellipsis (a wider box than the old chip, but still within the 20px height budget via a small font and single line, no wrap).
- **Privacy:** unchanged from `hanabi-notes.ts` — browser-local, keyed by card id, never rendered on a teammate's tile, never sent to the server.
- **Touch target:** the 20px visible box is padded with an out-of-flow inset span to reach 44px, matching the project's established pattern.

## Board Layout (BOARD-01..05)

- **Play area (top of the left column):** subtle `1px solid var(--color-border)` outline with rounded corners, a `"Play"` label (Label role, `--color-text-muted`) inset top-left of the outline, containing every stack's fanned tiles (horizontal fan, per Height Budget § above).
- **Discard area (bottom of the left column):** same outline/label treatment, `"Discard"` label, containing the shared, rearrangeable discard order (DISC-01, below).
- **Deck counter (between Play and Discard):** `"48"` (Label role, `--color-text`) beside a small `FireworkCardBack` rendered at a reduced size (~32×44px) — reuses the existing picture-frame back component, no new asset (D-21).
- **Clue/fuse token column (right of the left column, `items-stretch` sibling — see Height Budget):** clue tokens (black disc + blue "?") in a vertical line, fuse tokens (black disc + yellow explosion/orange-red rim) immediately beside/below the clue tokens in the same column, both on the right per the owner's literal description (D-16/D-18). **Spent tokens are removed from the column entirely** (BOARD-03, D-19) rather than dimmed — the column's token count shrinks as clues/fuses are spent, and a text count (e.g. `"3 clues left"` / `"2 fuses left"`, Label role, `--color-text-muted`) sits beside the column for accessibility and for test assertions, always present regardless of token count.
- **Played stacks (BOARD-05):** every card in a stack visible via horizontal fan, per Height Budget § above — not just the top card.

## Shared Discard Order (DISC-01)

Client presentation only — the server-authoritative mechanics (new `reorderDiscard` action, `HanabiState.discardOrder`, `HanabiViewSchema` field) are fully specified in 06.2-RESEARCH.md Pattern 2 and are not a design-contract concern beyond the following UI requirements:

- The Discard area (Board Layout § above) renders every discarded tile in `HanabiView.discardOrder`'s exact order — identical on every player's screen.
- Any seated player can pointer-drag any tile within the discard area to a new position, using the same pointer-event drag architecture as hand reorder (`useHandDrag.ts`/`hanabi-drag-logic.ts` pattern, mirrored into a new `hanabi-discard-drag-logic.ts` per RESEARCH.md), dispatched through the same `act()` chokepoint as every other action.
- **Optimistic order + reconciliation:** while a drag is in flight, the dragging player's own view shows the pending order immediately; a stale rejection (another discard landed mid-drag) silently reconciles to the server's confirmed `discardOrder` on the next frame — no error toast, no confirmation dialog (D-27, last-write-wins).
- **No per-seat ownership affordance:** unlike own-hand reorder, every seated player's pointer can drag every tile in the discard area — there is no "this isn't your tile" disabled state, since D-25 makes this a shared workspace by design.
- Visual treatment of an individual discarded tile matches the existing discard-entry sizing/art (suit glyph + tile-back styling per 06.1), unchanged by this phase except for the new drag affordance and the shared ordering.
