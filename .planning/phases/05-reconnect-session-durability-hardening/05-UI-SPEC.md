# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope guardrail (read first):** This phase adds no new screens and no new visual system. Per CONTEXT.md and the phase objective, the surface is three small, additive changes at Phase 4's deliberately plain fidelity:

1. A "Reconnecting…" banner over the last known view, with all action controls disabled (D-05).
2. Per-seat connection status on `HanabiBoard.tsx` (currently absent — the lobby's `SeatRow` already has it, the board does not), plus explicit "Waiting for {name} — disconnected" turn text when the active player is absent (D-07).
3. A "Use this tab" button on the superseded-tab screen in `RoomClient.tsx` (D-11).

No new palette, typography, spacing, or component-library work happens in this phase. Every token below is inherited unchanged from `01-UI-SPEC.md`, reconfirmed unchanged by `02-UI-SPEC.md` and `04-UI-SPEC.md`. Do not design Phase 6's board, do not add card art, animation, glyphs, or luminosity work, and do not polish `HanabiBoard.tsx` beyond what D-05/D-07 require. Produced in `--auto` mode from CONTEXT.md, RESEARCH.md, `01-UI-SPEC.md`, `04-UI-SPEC.md`, and the current source of `SeatRow.tsx`, `RoomClient.tsx`, `HanabiBoard.tsx`, `room-store.ts`, and `apps/web/app/globals.css` — no new user interaction required.

**This phase's specific role mapping (not new sizes — reuses the four above):**
- Reconnecting banner text → **Label** role, `--color-text` (must read clearly at a glance, unlike a muted caption — the player needs to notice it immediately).
- Per-seat connection status label on the board ("Connected"/"Disconnected") → **Label** role, `--color-text-muted`, exactly matching `SeatRow`'s existing lobby treatment — do not invent a different size for the same fact rendered in a new location.
- "Waiting for {name} — disconnected" turn text → **Body** role, same slot and color rules as the existing turn indicator (`--color-text-muted` when not the viewer's turn; this text never renders in the accent color, since a disconnected active player is never the viewer's own turn state).
- "Use this tab" button label → **Label** role (matches `Button`'s existing label typography, unchanged).

Only two weights exist (400, 600) — unchanged. No third weight or typeface introduced.

## Color

**Palette unchanged from Phase 1's dark "fireworks night" tokens. No new hex values this phase.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0F1A` (`--color-bg`) | Page/board background, unchanged |
| Secondary (30%) | `#141A2E` (`--color-surface`) | Reconnecting banner background, superseded-screen card background (reuses the existing centered-card shell already used for refusal/superseded screens) |
| Accent (10%) | `#F5B942` (`--color-accent`) | **Reserved for, this phase specifically:** the "Use this tab" button fill (it is a primary action — reclaiming the seat — so it reuses `Button variant="primary"` unmodified, accent fill + `--color-bg` label). Nothing else new this phase uses accent. The reconnecting banner does **not** use accent — a banner announcing degraded connectivity is not a call to action, and accent must stay reserved for the existing five-item list Phase 1 locked (see `globals.css` header comment); "Use this tab" is the one legitimate sixth addition, since it is a primary CTA button in the same family as "Create room"/"Join room"/"Start game". |
| Destructive | `#F0453D` (`--color-destructive`) | Not used by this phase. A reconnecting/disconnected state is an expected, non-error condition (per Phase 1's own precedent: "a disconnected teammate is an expected, non-error state... not a failure needing alarm-red") — reusing `--color-status-disconnected` (slate), never destructive-red, for any disconnected indicator this phase touches. |

**Connection-status color (reused verbatim from Phase 1, not redefined):**

| Token | Value | Usage this phase |
|-------|-------|-------------------|
| `--color-status-connected` | `#34D399` | Per-seat status dot on `HanabiBoard.tsx`, when connected — **always paired with the text label "Connected"**, never color alone (Phase 1's accessibility rule applies unchanged) |
| `--color-status-disconnected` | `#6B7280` (slate) | Per-seat status dot on `HanabiBoard.tsx`, when disconnected — **always paired with the text label "Disconnected"** |

**Reconnecting banner:** `--color-surface` fill, `--color-border` outline (or bottom border, if implemented as a top-of-screen strip — Claude's discretion on exact placement per D-04/discretion note below), `--color-text` label text (Label role, not muted — this must be legible immediately, not a background caption). No accent, no destructive. A small status dot may reuse `--color-status-disconnected` next to the banner text if a dot reads better than text alone, but the text label ("Reconnecting…") is mandatory regardless — dot is optional decoration, never the sole signal.

**Contrast rule:** unchanged from Phase 1/2/4 — accent fills always pair with `--color-bg` text/labels (≈10.9:1, WCAG AA pass), never `--color-text` (≈1.63:1, fails AA). Applies to the "Use this tab" button, which reuses `Button variant="primary"` unmodified.

**Accent reserved for (explicit list, this phase, additive to Phase 1's five):** primary CTA fills (unchanged: "Create room"/"Join room"/"Start game"/Play/Discard/Give-clue), room-code Display text, own-seat "you" ring, active-turn indicator text, focus rings, **plus** the "Use this tab" button fill (new, sixth item — same category as the existing primary-CTA usages, not a new kind of accent use). No other element introduced this phase uses accent.

## Screens & States (Phase 5 scope)

No new screens. Three existing screens/components gain additive states:

1. **`HanabiBoard.tsx` — per-seat connection status (D-07, RT-06).**
   Each rendered hand (own hand's seat label included, per `SeatRow` precedent of always showing status even for the viewer) gains a connection-status dot + label, placed next to the existing seat label ("{displayLabel}'s hand" / lobby-equivalent), using the exact dot-plus-text idiom from `SeatRow.tsx` (`xs` gap, dot as an `aria-hidden` 8px circle, label in Label role/`--color-text-muted`). This is read from the existing `connected` field already present in `RoomView.seats[]` (per RESEARCH.md's confirmed `toSeatView` flow) — no new server field, purely additive rendering.
   The turn indicator (`data-testid="turn-indicator"`, unchanged element) appends " — disconnected" to its existing "Waiting for {name}" string whenever `view.seats.find(s => s.seatId === activeSeatId).connected === false`. It never changes color to destructive-red (see Color section) — disconnected-but-your-teammate remains a slate/muted signal, not an alarm.

2. **`HanabiBoard.tsx` (and any other in-progress screen) — "Reconnecting…" banner (D-05).**
   Rendered as a `md`-padded, `--color-surface`-filled, `--color-border`-outlined strip anchored at the top of the existing page content (above the turn indicator, inside the same `<main>` — not a full-screen takeover, not a modal) whenever the store's connection-state flag is `"reconnecting"` (the store keeps the last-received `view` and adds this flag per D-05/RESEARCH.md's Architecture Diagram — no new full-screen "Connecting to room…" state is shown once a view has been received at least once). While this banner is visible: Play, Discard, Give-clue, the clue-target/value pickers, and slot selection all render in their existing disabled visual treatment (same `Button` disabled styling already defined by Phase 4 — no new disabled-state color is introduced). The banner disappears the instant a fresh `joined`/`state` frame arrives and the flag clears — no fade animation required, a plain conditional render is sufficient at this phase's fidelity.
   Exact placement (top-of-page strip vs. a bar directly above the turn indicator) and whether a status dot accompanies the text are Claude's discretion per RESEARCH.md's "Store shape for the reconnecting state and banner placement and wording" discretion item — the requirement is: visible without scrolling, does not obscure hand contents, and unambiguous that it means the connection, not the game, is the thing that's stalled.

3. **`RoomClient.tsx` — superseded screen gains "Use this tab" (D-11).**
   The existing superseded-screen card (`--color-surface`... actually currently rendered as bare centered text on `--color-bg`, per current source — this phase does not change that shell) keeps its unchanged heading text ("This room was opened in another tab.") and adds, below it with `md` gap, a `Button variant="primary"` labeled "Use this tab". On click: resets the `stopReconnectingRef` latch and calls the socket's reconnect path with the same stored seat token (implementation detail — Claude's discretion per RESEARCH.md whether this goes through `reconnect()` or a remount), which supersedes the other tab per Phase 1's existing newest-tab-wins rule (D-10/D-08, unchanged). No confirmation dialog (see Copywriting Contract, Destructive actions). While the reclaim is in flight, the button may show its own transient disabled/pending state (matching `Button`'s existing disabled treatment) rather than double-firing on a second click — this mirrors the existing "Copy link" button's transient-label pattern from Phase 1, but is not required to swap its label text, only to prevent a duplicate reconnect call.

No other screens change this phase. Create-room, join, lobby (non-board), and refusal screens are untouched.

## Component Notes

- **No new shared design-system components required.** The per-seat connection dot on the board reuses `SeatRow`'s exact visual pattern (do not redefine the dot's size, color logic, or label copy — copy the idiom, not a new one). The reconnecting banner and "Use this tab" button are new but compose entirely from existing primitives (`Button`, plain divs styled with the existing CSS custom properties) — neither requires a new entry in the Phase 1 design-system contract.
- **Data flow, not new data.** `RoomView.seats[].connected` already exists and already flows through `toSeatView` (confirmed by RESEARCH.md's Architectural Responsibility Map: "The `connected` flag already flows through `toSeatView`; this phase only adds board-level rendering, not new server logic"). This phase's board changes are purely additive rendering of data already on the wire — no new schema field, no new wire message type is introduced by the UI layer itself (the heartbeat/zombie-sweep mechanism that keeps `connected` truthful is a worker-side concern, out of this document's scope).
- **Trap — do not conflate "reconnecting" with "disconnected."** These are two different signals rendered in two different places: the reconnecting banner describes the *viewer's own* socket state (client-side, ephemeral, cleared the instant their own socket recovers); the per-seat disconnected label describes *any seat's* (including possibly the viewer's own, from another player's perspective) server-tracked `connected` flag. Do not merge these into one indicator or one code path — they answer different questions ("is my connection to the server currently degraded?" vs. "is this named player currently reachable by the server?").
- **Stable `data-testid` hooks required, extending Phase 4's list (per D-14's Playwright plan):** `reconnecting-banner`, `seat-status-{seatId}` (per-seat connection dot+label group on the board), `use-this-tab-button`. These are additive to Phase 4's existing floor list (`turn-indicator`, `own-hand`, etc.), which remain unchanged and must not be renamed.
- Use `clsx` for conditional class composition (banner visible/hidden, per-seat connected/disconnected dot color, disabled control states) per `CLAUDE.md`'s locked stack — no `tailwind-merge` needed at this phase's component complexity.
- **Do not build a per-error-reason copy system.** Per Phase 4's precedent and this phase's own scope boundary, connectivity issues are communicated entirely through the banner + per-seat status labels already specified; a richer reason-by-reason toast system remains explicitly out of scope (Phase 6 or later, if ever).
