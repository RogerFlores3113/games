## Color

Palette: dark "fireworks night" (unchanged base, Phase 1 D-16). Phase 6 **extends** `apps/web/app/globals.css`'s `@theme` block with suit-hue tokens and one card-glow token; it does **not** redefine any existing token (`--color-bg`, `--color-surface`, `--color-accent`, `--color-destructive`, `--color-text`, `--color-text-muted`, `--color-border`, `--color-status-connected`, `--color-status-disconnected` all carry over unchanged).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0F1A` (`--color-bg`, inherited) | Page/board background |
| Secondary (30%) | `#141A2E` (`--color-surface`, inherited) | Card backgrounds, tableau panels, end-overlay card |
| Accent (10%) | `#F5B942` (`--color-accent`, inherited) | **Unchanged reserved list, extended per D-02 with two in-game uses:** primary CTA fill (unused in-game except "New game"), active-turn seat ring/glow, own-seat "you" marker, focus rings, **plus (D-02, new this phase): the active-player hand-container ring/glow and the own-hand "Your turn" state background accent.** No other element uses it. |
| Destructive | `#F0453D` (`--color-destructive`, inherited) | Fuse-lost flash / fuse-token depleted state only (new use this phase, still within the existing "error/danger" semantic — not a new color) |

**New suit-hue tokens** (added to `@theme`, additive only):

| Token | Value | Contrast vs `--color-bg` | Contrast vs `--color-surface` |
|-------|-------|--------------------------|-------------------------------|
| `--color-suit-red` | `#F0645A` | 6.08:1 (AA pass) | 5.49:1 (AA pass) |
| `--color-suit-yellow` | `#E8C547` | 11.40:1 (AA pass) | 10.28:1 (AA pass) |
| `--color-suit-green` | `#4FBF8A` | 8.34:1 (AA pass) | 7.52:1 (AA pass) |
| `--color-suit-blue` | `#6FA8FF` | 7.95:1 (AA pass) | 7.17:1 (AA pass) |
| `--color-suit-white` | `#E7ECF7` | 16.16:1 (AA pass) | 14.58:1 (AA pass) |
| `--color-suit-rainbow` | `#C9A8FF` | 9.59:1 (AA pass) | 8.65:1 (AA pass) |
| `--color-suit-black` | `#B7C2D6` | 10.66:1 (AA pass) | 9.62:1 (AA pass) |

All seven verified via the WCAG relative-luminance formula this session (`node` one-off script against `--color-bg`/`--color-surface`), **all pass AA (≥4.5:1) against both backgrounds**. Pitfall avoidance: `--color-suit-black` is deliberately a light silver, not literal near-black, per RESEARCH.md Pitfall 1 — Black's suit identity is carried by its glyph silhouette and label, never by rendering it dark-on-dark.

**Critical structural decision for D-10's "verify contrast at the dimmest step" requirement:** suit hue and glyph fill render at **one constant, full-opacity value across all three luminosity steps** — luminosity is expressed *exclusively* through the card **frame** (border color/width, background tint, box-shadow), never by dimming the glyph or hue itself. This means the contrast table above is not just the "brightest step" number — **it is the contrast at every step, including the dimmest ("unclued")**, because the glyph/hue channel never changes. This is a deliberate departure from RESEARCH.md's illustrative `opacity-80` sketch for the unclued state (Pattern 1 code example) — reducing whole-card opacity would degrade suit-hue contrast at exactly the step D-10 requires verifying, so the spec instead confines all luminosity signaling to frame properties, leaving glyph/hue opacity untouched at 100%.

**New card-glow token** (frame luminosity signal, distinct from `--color-accent` — this is a card-state signal, not one of the accent's five reserved interactive uses):

| Token | Value | Usage |
|-------|-------|-------|
| `--color-card-glow` | `#FFD98A` (warm gold-white, distinct hue from `--color-accent`'s `#F5B942` so the two are visually distinguishable when both appear near each other — e.g. an active player's own lit card) | Card-frame box-shadow/border for the "touched" and "known" luminosity steps only. Never used for suit identity, never used for the accent's reserved interactive purposes. |

**Accent reserved-for list (explicit, extended from Phase 1, still exhaustive):** primary CTA fill ("New game" only, in-game), room-code Display text (not used in-game), own-seat "you" ring, active-turn hand-container ring/glow, own-hand "Your turn" state accent, focus rings on all interactive controls. Nothing else uses `--color-accent`. `--color-card-glow` is a **separate token** specifically so luminosity signaling never collides with or dilutes the accent's reserved meaning.

**Verified token pairs (Phase 1, still valid):** text-muted/bg ≈6.2:1 · text-muted/surface ≈5.6:1 · text/surface ≈16:1 · accent-text/bg ≈10.9:1 · destructive/surface ≈4.6:1.

**Accessibility forward-compatibility note (fulfilled this phase):** Phase 1 flagged that "luminosity- and glyph-based signaling [in Phase 6] will extend th[e] same 'never color-alone' rule" — fulfilled by D-05 (glyph + hue always paired, never hue alone) and by luminosity being a frame property that is legible in grayscale (border width and glow intensity, not just a color shift).

## Layout

**Fixed three-band desktop layout (D-01).** No scrolling required at ≥1280×720 for 5 players; usable with vertical scroll permitted down to ~1024px wide.

### Viewport: 1280×720 (reference/no-scroll target)

```
┌─────────────────────────────────────────────────────────────┐ 720px
│ ReconnectingBanner (conditional, ~40px, overlays top edge)   │
├─────────────────────────────────────────────────────────────┤
│  TOP BAND — teammate hands, ~168px fixed height              │
│  turn order starting after viewer, left→right, flex row,     │
│  gap: --space-md (16px), centered, wraps to 2 rows only      │
│  below ~1024px width (4 teammates max at 5-player table)     │
├─────────────────────────────────────────────────────────────┤
│  CENTER BAND — tableau, flexible height (fills remainder,    │
│  ~304px at 720 total), flex-1 min-h-0                        │
│    Row 1: stacks (5–6 heads) + clue tokens + fuse tokens      │
│    Row 2: deck-count/final-round + discard pile               │
├─────────────────────────────────────────────────────────────┤
│  BOTTOM BAND — own hand + action controls, ~208px fixed       │
│  height: turn indicator, own-hand cards row, Play/Discard/    │
│  clue-picker controls                                         │
└─────────────────────────────────────────────────────────────┘
```

Exact band heights (desktop, 1280×720): top band `168px` (seat label 20px + card row 100px + status row 20px + `--space-sm` gaps + `--space-md` padding), center band `flex-1 min-h-0` (fills remaining ~304px after top/bottom/gaps), bottom band `208px` (turn indicator 24px + card row 120px + controls row 44px + gaps/padding). Band gaps: `--space-md` (16px) between bands. Outer page padding: `--space-md` (16px) horizontal, `--space-sm` (8px) vertical (tighter than Phase 1's non-game screens, since every pixel of vertical space is load-bearing for the no-scroll requirement at 720px).

**Container structure:** `<main class="flex min-h-screen flex-col overflow-y-auto">` with three direct children: `<div class="flex-none">` (top band), `<div class="flex-1 min-h-0 overflow-visible">` (center band — uses `flex-wrap` internally so its two rows can wrap to three at narrow widths rather than clipping), `<div class="flex-none">` (bottom band). `overflow-y-auto` on `<main>` is what permits D-01's "may scroll down to ~1024px" without any band-specific scroll containers (avoids nested-scroll UX bugs).

### Viewport: 1024px wide (minimum supported, may scroll)

- Top band: teammate hand cards shrink from 56×78px to 48×68px (see Card Anatomy sizing table); 4 teammates still fit in one row at 1024px (4 × ~120px hand width + 3 × 16px gaps ≈ 528px, well within 1024px), so wrapping in practice only triggers below ~700px, which is out of scope (UI-11 targets "common desktop window sizes," not tablet widths) — documented here so the executor does not over-build a breakpoint that is never exercised.
- Center band: stack heads and discard entries shrink to the same 48×68px card size; token/count text remains at the Body role size (16px, unchanged — legibility of numbers is never sacrificed for layout).
- Bottom band: own-hand cards shrink from 72×100px to 60×84px; action-button row stays at 44px minimum height (touch-min token) regardless of width.
- Total page height may exceed 720px at 1024px width if a 5-seat game's top band wraps or center-band content grows (e.g. a long discard pile) — `<main>`'s `overflow-y-auto` handles this; no band is individually clipped.

## Suit Identity System (UI-06, groundwork for UI-07)

All seven suits are defined now (D-06), each with a **unique glyph silhouette + fixed hue**, both always rendered together — hue is never the sole carrier of identity (D-05).

| Suit | Hue token | Glyph shape (distinct silhouette) | Notes |
|------|-----------|-------------------------------------|-------|
| Red | `--color-suit-red` (`#F0645A`) | 5-point star (filled) | |
| Yellow | `--color-suit-yellow` (`#E8C547`) | Solid triangle, point up | |
| Green | `--color-suit-green` (`#4FBF8A`) | Solid square | |
| Blue | `--color-suit-blue` (`#6FA8FF`) | Solid circle | |
| White | `--color-suit-white` (`#E7ECF7`) | Solid diamond (rotated square) | Lightest hue; glyph shape (diamond) is what distinguishes it from a plain "white card," not the hue's lightness alone |
| Rainbow | `--color-suit-rainbow` (`#C9A8FF`) | 8-point starburst, **flat single-tone fill** (no gradient in the silhouette itself) | Per D-06/RESEARCH.md Pitfall 2: the burst shape alone must read as "rainbow" in grayscale; a thin decorative multicolor ring may be layered *around* (never *replacing*) the flat-fill starburst as garnish only |
| Black | `--color-suit-black` (`#B7C2D6`) | Hexagon with a notch (distinct from all six others) | Per Pitfall 1: rendered as light silver, never literal near-black — its "blackness" is its name/glyph, not its lightness |

**Rendering rule (D-05, no exceptions):** the glyph + hue pair appears on every suit reference: face-up teammate cards, stack heads, discard-pile entries, color-clue picker buttons, positive/negative clue marks, and own-hand candidate-strip pips. No toggle exists to hide or add this — it is always on.

**Implementation constraint (RESEARCH.md anti-pattern, binding):** suit-to-class-name mapping must use a **static literal lookup object** (e.g. `{ red: "fill-[var(--color-suit-red)]", ... }`), never a runtime-interpolated Tailwind class string (`` `fill-suit-${suit}` ``) — Tailwind v4's JIT scanner cannot see dynamically built class names.

## Luminosity System (UI-08, UI-09)

Three discrete steps (D-08), derived from a card's `facts` alone, expressed **exclusively via the card frame** (border, background tint, box-shadow) — never via hue or glyph opacity (D-10):

| Step | Trigger | Frame treatment |
|------|---------|------------------|
| **Unclued** | No positive clues (`facts.positiveClues.length === 0`) | `border: 1px solid var(--color-border)`; `background: var(--color-surface)`; `box-shadow: none`. Card reads as a dim, unlit shell. |
| **Touched** | ≥1 positive clue, not fully known | `border: 2px solid var(--color-card-glow)`; `background: var(--color-surface)`; `box-shadow: 0 0 8px 0 rgba(255, 217, 138, 0.35)`. |
| **Known** | `possibleSuits.length === 1 && possibleRanks.length === 1` | `border: 2px solid var(--color-card-glow)`; `background: var(--color-surface)`; `box-shadow: 0 0 16px 0 rgba(255, 217, 138, 0.65), 0 0 4px 0 rgba(255, 217, 138, 0.9)`; `filter: brightness(1.08)` on the frame only (never on the glyph fill, since suit hue must not shift — apply `filter` to a background layer element, not the glyph `<svg>`). Card reads as the "fully lit firework." |

Negative-only information (candidates narrowed via `negativeClues` but zero `positiveClues`) stays at **Unclued** — a card nobody pointed at must not look chosen (D-08's explicit anti-goal).

Applies identically to **teammates' face-up cards** using their own `facts` (D-09) — every player sees at a glance what a card's holder currently knows, not just their own hand.

**Performance guard (RESEARCH.md Pitfall 5):** use `box-shadow` for all card-frame glow (cheap, applied to a handful of rectangular elements). Reserve `filter: drop-shadow(...)` exclusively for the one-at-a-time stack-complete celebratory flash (below) — never apply `filter: drop-shadow` per-glyph across a full hand or candidate strip.

### Fireworks-night motion (D-11, D-22)

- **Static base:** dark layered background (`--color-bg` base, no new gradient token needed — reuse existing surface/border tokens for subtle panel separation). No particle system, no continuously-running animation.
- **Transient clue-touch highlight (D-14):** when a clue lands, cards in `touchedCardIds` (from the latest `history` clue entry) get a **2-second** outline pulse — `box-shadow: 0 0 0 3px var(--color-card-glow)` animating to the card's settled luminosity-step shadow via a CSS `transition` (`transition: box-shadow 2s ease-out`), then the persistent `facts`-derived frame takes over. No JS timer needed beyond a CSS `animation` with `animation-fill-mode: forwards` triggered by a class toggled for 2s (or a keyframe with a 2s total duration) — client memory is not required since the persistent marks re-derive from `facts` on every render.
- **Stack-complete flash (D-11):** when a stack reaches rank 5, a **600ms** flash — `filter: drop-shadow(0 0 24px rgba(255,217,138,0.9))` on that stack head only, applied via a CSS `@keyframes` (opacity/scale pulse from 1 → 1.08 → 1), single-shot, `animation-iteration-count: 1`.
- **Reduced motion:** wrap both animations in `@media (prefers-reduced-motion: reduce) { animation: none; transition: none; }` — the transient highlight and stack-complete flash both **degrade to an instant style swap with no animated transition**, never disappearing entirely (the persistent luminosity-step change and the fact that a stack completed must still be visible, just without motion).

## Card Anatomy

### Sizing (by context)

| Context | Size (≥1280px) | Size (1024px) | Glyph size | Rank numeral size |
|---------|------------------|-----------------|------------|---------------------|
| Teammate face-up card | 56×78px | 48×68px | 20px | 16px (Label weight 600) |
| Own-hand face-down card | 72×100px | 60×84px | 28px (confirmed) / 12px (candidate pips) | 22px (confirmed) / 12px (candidate pips) |
| Stack head / discard entry | 48×64px | 48×64px (unchanged — legibility floor) | 18px | 14px |

### Teammate face-up card (visible identity)

- Frame: luminosity-step border/glow (above) around a `--color-surface` card body, `border-radius` matching existing `Button`/`SeatRow` radius convention (read from existing components; do not introduce a new radius token).
- Content: `SuitGlyph` (hue-filled) centered top, rank numeral (Label weight, `--color-text`) centered below it.
- Candidate/clue marks (D-13): a compact strip below the rank numeral, same visual language as the own-hand candidate strip but at a smaller scale (10px pips) — shows what the *holder* knows about their own card, not new information for the viewer (the face-up identity is dominant; the strip is secondary).

### Own-hand card (face-down, no identity beyond narrowed facts — D-15 hard rule)

Two-zone anatomy, top 60% / bottom 40% of the card body:

1. **Confirmed-info zone (top):** renders a suit glyph **only if** `possibleSuits.length === 1` (using that one suit's hue+glyph), and a rank numeral **only if** `possibleRanks.length === 1`. If neither has narrowed, this zone shows a **blank card-back glyph** (a simple centered outline square, `--color-border` stroke, no fill — decorative "unknown" placeholder, carries zero suit/rank information by construction). Partial narrowing (e.g. suit known, rank not) shows only the known half; the other half stays blank. This structurally enforces D-15: the glyph/numeral components are only ever invoked with a length-1 array, so there is no code path that could render an unnarrowed identity.
2. **Candidate strip (bottom):** two compact rows —
   - **Suit pips row:** one small glyph per variant suit (in `ALL_SUITS`/`cluableColors` order), each rendered at `opacity: 1` if still in `possibleSuits`, or `opacity: 0.25` + a diagonal strike-through overlay if ruled out.
   - **Rank pips row:** numerals 1–5, same present/struck treatment driven by `possibleRanks`.
   - Pip sizing: 12px glyphs/numerals, `--space-xs` (4px) gaps.
- Frame: same luminosity-step system as teammate cards, computed from the same `facts`.
- **Hard rule (D-15, carried from Phase 4):** the derivation functions that produce this anatomy (`candidateDisplayFor`, the confirmed-glyph/numeral logic) accept only `ClueFactsView` — a type with no `suit`/`rank` fields — making an identity leak a compile-time impossibility, not just a runtime discipline. Unit-tested per D-23.

## Action Interaction (RULES-11)

**Select-then-act (D-16), no confirmation dialog:**
- Click an own-hand card → selects it, reveals **Play** and **Discard** buttons scoped to that card (preserves `data-testid="play-button"` / `data-testid="discard-button"`, preserved from the interim board).
- Click a teammate's hand → selects that teammate, reveals the clue picker: cluable colors (variant's `cluableColors`) + ranks 1–5 as a button grid (preserves `data-testid="clue-target-{seatId}"`, `data-testid="clue-value-{color|rank}"`, `data-testid="give-clue-button"`).

**Clue preview (D-17):** hovering **or focusing** a clue-value button highlights (via the transient-highlight treatment above, sustained while hover/focus persists rather than timed) exactly the teammate cards `clueTouchIdsForTarget` returns. Options that touch zero cards render **disabled**, never hidden.

**Disabled-reason copy (D-18) — exact strings, extending existing patterns verbatim where they already exist:**

| Condition | Copy | Status |
|-----------|------|--------|
| Not your turn | *(no separate caption — action controls simply do not render for a non-active player's own hand; teammate hands never show a clue picker unless it is the viewer's turn)* | Existing behavior, preserved |
| No clue tokens left | "No clue tokens left" | **Preserved verbatim** from `HanabiBoard.tsx` |
| Discard disabled at 8 tokens | "Clue tokens are full — you can't discard" | **Preserved verbatim** from `HanabiBoard.tsx` |
| Clue touches nothing | "That clue wouldn't touch any of {name}'s cards" | **Preserved verbatim** (template string, `labelFor(clueTarget)`) |
| Reconnecting | "Reconnecting…" (banner, unchanged) | **Preserved verbatim** from `ReconnectingBanner.tsx`; all action controls additionally get `disabled` while `reconnecting` is true (existing behavior) |

All reasons render as **visible inline text** (`--color-text-muted`, Label role), never a bare `title` attribute alone (RESEARCH.md anti-pattern — `title` is inconsistently exposed to keyboard/screen-reader users) — matches the interim board's existing `noTouchCaption` pattern exactly.

**Keyboard reachability (D-19):** every interactive element is a native `<button>` (existing pattern) with the browser's native `:focus-visible` ring styled via `--color-accent` (reuses the accent's "focus rings" reserved use from Phase 1). No custom `tabIndex`/keydown handling, no custom shortcut scheme. Hover-driven clue preview has an exact focus equivalent (same highlight, triggered by `:focus-visible` as well as `:hover`).

## End of Game (UI-10, D-20/D-21)

**Overlay:** `position: fixed; inset: 0;` with a `background: rgba(11, 15, 26, 0.7)` backdrop (derived from `--color-bg` at 70% — a scrim, not a new token) over the final board state. Board remains visible and rendered behind the overlay; every action control is `disabled` (reuses the existing `reconnecting`-style disable pattern, gated on `view.status === "ended"` instead).

**Overlay card:** centered, `--color-surface` background, `--color-border` border, `--space-lg` (24px) padding, matching Phase 1's `RefusalCard` visual weight (same "one centered card on a scrim" pattern, reused for consistency rather than invented fresh).

**Content (top to bottom):**
