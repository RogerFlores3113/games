# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder (binding):** Phase 8 introduces **zero new visual design**. It only (1) makes the landing page's "Create room" path work before hydration, (2) swaps the disabled game-picker option from Innovation to Expedition with the exact same treatment, (3) makes the Hanabi settings fieldset and lobby copy read from per-game registry data instead of hardcoded Hanabi constants, and (4) defines the pending/error states on Create room. No new tokens, no new colors, no new components, no layout changes. Every value below is either a direct carry-forward from the shipped app (`apps/web/app/globals.css`, `apps/web/app/page.tsx`, `apps/web/components/Lobby.tsx`, `apps/web/components/Button.tsx`) or a minimal, explicitly-scoped addition (the pending/error copy strings, which did not exist before this phase in fully specified form).

## Component Notes (binding on the executor)

These are carry-forward constraints from the existing shipped components, restated here because the executor must not regress them while making the two screens game-agnostic:

1. **`Button.tsx`** stays exactly two variants (`primary`, `ghost`) — do not add a third for a "coming soon" or pending affordance. The disabled-state treatment (drops accent fill entirely to `--color-surface` + muted text + `--color-border` ring, never a faded/50%-opacity accent) is unchanged and applies to the D-17 pending state exactly as it does today.
2. **Landing page (`apps/web/app/page.tsx`)**: the settings fieldset (today: Hanabi's variant radios) must come from a per-game lookup, not an `isHanabi` boolean. Visually, Hanabi's fieldset (`Variant` legend, three-way radio row with `Base`/`Rainbow`/`Black` labels) renders byte-identically to today — same markup, same `--space-sm`/`--space-md` gaps, same `--text-label`/`--text-body` roles, same `--color-landing-text` colors. A game with no settings (test-only toy game; Expedition in a later phase) renders no fieldset at all, not an empty one.
3. **The "Create room" button's visibility must not be gated on `isHanabi` or any per-game conditional** — today it is nested inside `{isHanabi && (...)}` alongside the variant fieldset, which is part of the MGR-08 root cause (button doesn't exist in the DOM until a game is picked). The button and its pending/disabled state must be independent of which game is selected; only the settings-fieldset content varies by game.
4. **`Lobby.tsx`**: `MIN_PLAYERS`/`MAX_PLAYERS` imports from `@games/schema` are replaced by `view.limits.min`/`view.limits.max` (D-05); the segmented variant picker's visual treatment (selected state: `--color-bg` fill, `--color-accent` border + label; unselected: transparent fill, `--color-border` border, `--color-text` label) is unchanged and stays Hanabi-specific — Phase 8 does not need to generalize the variant picker itself to other games' settings shapes (Hanabi is the only game with in-lobby settings this phase; MGR-03 requires only that the *fieldset lookup* be per-game, not that a generic settings-renderer be built for hypothetical future shapes).
5. **Fireworks/photo backdrops, panel treatment, `RoomCode`, `SeatRow`, `ReconnectingBanner`, `PhotoCredit`** — all unchanged, not touched by this phase.
