<objective>
Fix "Create room" at the cause (MGR-08, D-17): the landing form works before hydration through a native POST to `/api/room` that mints a code and redirects, with the current JS flow kept as an enhancement; swap Innovation for a disabled "Expedition - coming soon" option and make the settings fieldset a per-game lookup (D-12, MGR-03); carry name/game/config to the room without touching the share link.

Design choice (D-17 leaves it to the planner): a short-lived cookie rather than a query parameter. Reasons: the URL is never polluted even transiently, so Copy link (which reads window.location.href) cannot leak in any timing window; and a Server Action was rejected because the installed Next.js docs state that in Client Components "forms invoking Server Actions will queue submissions if JavaScript isn't loaded yet" (node_modules/next/dist/docs/01-app/01-getting-started/07-mutating-data.md line ~170) — that still waits for hydration, which is exactly the flake's cause. A plain `action="/api/room" method="post"` form works with zero JS.

Pre-hydration settings visibility: the fieldset for the selected game is shown by CSS (`:has(option:checked)`), not React state, so choosing Hanabi reveals its variant radios before hydration too. All inputs are uncontrolled (the JS handler reads FormData), so typing before hydration is never clobbered — removing the reason the old `useHydrated` gate existed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> POST /api/room (JSON and form) | Untrusted creation input |
| Server -> browser cookie -> RoomClient | Cookie contents re-enter the client and are written to localStorage |
| Room URL -> shared link | Anything in the URL is disclosed to whoever receives the link |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-8-13 | Tampering | route.ts both branches | mitigate | CreateRoomRequestSchema (closed gameId, per-game config, strictObject) before minting; failure -> 400 JSON or 303 /?error=create |
| T-8-14 | Information Disclosure | share link | mitigate | Values never placed in the URL; e2e asserts empty query and exact clipboard text (D-17) |
| T-8-15 | Tampering | pending_room cookie | mitigate | Re-validated with CreateRoomRequestSchema on read; always expired after one read; Path=/room/{code}, Max-Age=120, SameSite=Lax, Secure on https; the worker still validates config on set_config |
| T-8-16 | Spoofing (CSRF) | POST /api/room | accept | Endpoint only mints a random code and sets a cookie for the submitter's own browser; no state or privilege changes server-side |
| T-8-17 | Information Disclosure | cookie not HttpOnly | accept | Holds only the submitter's own display name/game/config, which the page itself needs to read; no secret or seat token |
</threat_model>
