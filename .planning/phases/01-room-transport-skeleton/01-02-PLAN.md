Create `packages/rules/src/adapter.ts` exporting a generic `GameAdapter<TState, TAction>` interface with exactly five members and no others:

- `readonly id: string` — a stable adapter identifier persisted alongside room state (`"counter"` for the placeholder), so a deploy that swaps adapters is detectable.
- `createInitialState(input: { seatIds: readonly string[]; variant: Variant; seed: string }): TState` — deterministic given its inputs; `seed` is a string so Phase 3's RULES-19 deterministic shuffle needs no signature change.
- `applyAction(state: TState, actorSeatId: string, request: unknown): AdapterResult<TState>` — note `request: unknown`. The adapter, not the caller, parses and validates the payload. This is the boundary that makes "asserting state" structurally impossible at the seam.
- `toPlayerView(state: TState, seatId: string): unknown` — returns the projection for exactly ONE seat. There is deliberately no `toSpectatorView` and no zero-argument serializer; the absence of any whole-state serializer on this interface is what forces per-seat sends.
- `checkGameEnd(state: TState): GameEndResult | null` — `null` means the game continues.

Also export `type AdapterResult<TState> = { ok: true; state: TState; } | { ok: false; error: AdapterError }` where `AdapterError` is a closed union of string literals `"not_your_turn" | "invalid_action" | "game_over"`, and `type GameEndResult = { score: number; reason: string }`. Declare `export type Variant = "base" | "rainbow" | "black"` locally in this file rather than importing it from `@games/schema`. This is deliberate duplication of a three-member literal union: `packages/rules` must have ZERO dependencies (not even `@games/schema`), because FDN-02 requires the rules engine to be buildable and testable in complete isolation. `packages/schema` declares the canonical wire-level `Variant` in Plan 03; a compile-time test in Plan 04 asserts the two unions are mutually assignable, which is a stronger guarantee than an import and costs nothing.

Write a file-level doc comment on `adapter.ts` stating the three invariants a conforming adapter must uphold, because Phase 4's engine author will read this file and nothing else: (1) `applyAction` never mutates its `state` argument, (2) `applyAction` treats `request` as hostile input and validates it internally, (3) `toPlayerView` is pure and is the ONLY way state leaves the adapter.

Re-export everything from `packages/rules/src/index.ts` alongside the existing `RULES_SMOKE` constant.

  <action>
Create `packages/rules/src/counter-game.ts` exporting `counterGame: GameAdapter<CounterState, CounterAction>` with `id: "counter"`.

`CounterState` is `{ count: number; seatIds: readonly string[]; turnIndex: number; turnsTaken: number }`. `createInitialState` sets `count: 0`, `turnIndex: 0`, `turnsTaken: 0`, and copies `seatIds` in the order given (seat order is join order per D-12; the adapter does not reorder).

The only legal action is `{ type: "increment" }`. Parse `request` with a hand-written type guard — this package has zero dependencies, so no Zod — that accepts ONLY an object whose sole own key is `type` with value `"increment"`. Any extra own key — including `count`, `state`, `turnIndex`, or `seatIds` — makes the payload `invalid_action`. Rejecting on extra keys, not just on wrong shape, is what makes state-assertion structurally impossible.

`applyAction` returns `{ ok: false, error: "not_your_turn" }` when `actorSeatId !== state.seatIds[state.turnIndex]`, and otherwise returns a NEW state object with `count + 1`, `turnsTaken + 1`, and `turnIndex` advanced modulo `seatIds.length`. Never mutate the input.

`toPlayerView(state, seatId)` returns `{ count, activeSeatId, isYourTurn, turnsTaken }` where `activeSeatId = state.seatIds[state.turnIndex]` and `isYourTurn = activeSeatId === seatId` — the per-seat differentiation the UI-SPEC's counter screen renders ("Your turn" vs "Waiting for {name}"). It must NOT include `seatIds` — the room layer owns the seat list, and keeping it out here keeps the projection genuinely per-seat rather than a shared blob with a flag.

`checkGameEnd` always returns `null` — the placeholder has no end condition; Phase 2/4 supply a real one.

Write `counter-game.test.ts` covering: increment on your turn advances count and turn; increment out of turn returns `not_your_turn` and leaves state untouched (assert by deep-equality against the pre-state); `{type:"increment", count: 999}` returns `invalid_action`; a non-object and a wrong `type` return `invalid_action`; `toPlayerView` yields `isYourTurn: true` for exactly one seat and `false` for all others; and a full lap of N seats returns `turnIndex` to 0.

Export `counterGame` and its types from `packages/rules/src/index.ts`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WebSocket client → adapter | `applyAction`'s `request` argument originates from an untrusted browser; the room actor forwards it without interpreting it |
| adapter state → wire | `toPlayerView` is the only exit from game state to the network |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-04 | Elevation of Privilege | `counterGame.applyAction` | mitigate | Turn ownership is checked server-side against `actorSeatId`, which the room actor derives from the validated seat token — never from the message payload. Out-of-turn actions return `not_your_turn` and leave state unchanged. |
| T-1-09 | Tampering | `applyAction` request payload | mitigate | The action guard accepts ONLY `{type:"increment"}` and rejects any object with extra own keys, so a client cannot smuggle `count`/`turnIndex` state assertions. Enforced by an explicit test and by the fast-check fuzz property in Task 3. |
| T-1-10 | Denial of Service | `applyAction` on hostile input | mitigate | Conformance property test asserts `applyAction` never throws for any `fc.jsonValue()` input — an uncaught throw inside a Durable Object message handler would tear down the connection for every seat in the room. |
| T-1-11 | Information Disclosure | `toPlayerView` | mitigate | The interface has no whole-state serializer (grep-asserted), so there is no non-per-seat path to the wire. Phase 2 hardens the projection's contents; Phase 1 guarantees the shape of the chokepoint. |
</threat_model>
