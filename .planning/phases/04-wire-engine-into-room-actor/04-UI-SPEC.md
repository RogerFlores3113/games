# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope guardrail (read first):** This phase's UI surface is a **deliberately disposable** screen (`HanabiBoard.tsx`, replacing `ForeheadCardGame.tsx`), per CONTEXT.md D-11: "at the same bare fidelity as the toy screens." It exists to prove RT-01/RT-03/RT-09 against the real Hanabi engine and gets **replaced wholesale by Phase 6** (UI-01…UI-11, RULES-11), which owns the colorblind glyph system, luminosity-as-signal theming, persistent clue-memory rendering, and the designed end-of-game screen. **No new palette, typography, spacing, or component-library work happens in this phase.** Every token below is inherited unchanged from `01-UI-SPEC.md` (and confirmed unchanged by `02-UI-SPEC.md`) — this document only maps those existing tokens onto Hanabi's screen shape and adds the phase-specific copy and layout rules. Produced in `--auto --chain` mode; all questions below were answered from CONTEXT.md, RESEARCH.md, `01-UI-SPEC.md`/`02-UI-SPEC.md`, and `packages/rules/src/hanabi/state.ts` with no new user interaction required.

**Do not polish this screen.** Per CONTEXT.md `<specifics>`: "The interim board should look unfinished on purpose... a half-polished Phase 4 board invites both wasted effort and premature attachment." No card art, no animation, no glyph system, no luminosity work.

## Spacing Scale

Declared values (must be multiples of 4) — **identical to Phase 1/2, inherited via `--space-*` CSS custom properties already defined in `apps/web/app/globals.css`. No new tokens.**

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, clue-fact chip inline padding |
| sm | 8px | Compact element spacing (card-slot gaps within a hand, clue-fact chip gaps) |
| md | 16px | Default element spacing (hand-to-hand row spacing, control group internal padding) |
| lg | 24px | Section padding (board-section separation: own hand / other hands / table / controls) |
| xl | 32px | Layout gaps (space between the table row — stacks/discard/tokens — and the hands above/below it) |

| 3xl | 64px | Page-level spacing (vertical page padding, matching the toy's existing layout) |

Exceptions: `--size-touch-min: 44px` (unchanged) — every play/discard/clue-target/clue-value button uses this minimum touch target, matching Phase 1/2's precedent.

## Typography

**Identical to Phase 1/2's declared scale — reused via existing `--text-*` CSS custom properties. No new sizes or weights.**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.5 |
| Heading | 24px | 600 (semibold) | 1.2 |
| Display | 40px | 600 (semibold) | 1.2 |

**Board-specific role mapping (not new sizes — reuses the four above):**
- Visible card identity text (other hands, discard pile, played stacks) → **Heading** role, `--color-text` (e.g. "R3", "Y5" — a two-character suit-letter + rank string is sufficient this phase; Phase 6 owns the real card face/glyph design).
- Seat labels above each hand, clue-fact chip text → **Label** role, `--color-text-muted` for seat labels, `--color-text` for clue-fact chip text (chips must be legible, not muted, since they are the only information the viewer has about their own hand).
- Turn indicator, clue/fuse token counts, deck count, score → **Body** role.
- End-of-game score → **Heading** role (not Display — Display stays reserved for the room code per Phase 1's contract; this matches Phase 2's precedent of using Heading rather than Display for a secondary hero number).

Only two weights exist (400, 600) — unchanged. No third weight or typeface introduced.

## Color

**Palette unchanged from Phase 1's dark "fireworks night" tokens. No new hex values this phase.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0F1A` (`--color-bg`) | Board screen background, matching every other screen |
| Secondary (30%) | `#141A2E` (`--color-surface`) | Every card tile (own-hand slots, other hands, played stacks, discard pile), the control-group panel background |
| Accent (10%) | `#F5B942` (`--color-accent`) | **Reserved for, this phase specifically:** the enabled play/discard/clue submit buttons (primary Button, accent fill + `--color-bg` label), the turn indicator text when it is the viewer's own turn, the "you are here" ring on the viewer's own hand row (inherited SeatRow pattern), and the currently-selected clue target/value in the clue-picker (selected-state ring only — not a fill, to avoid a second accent-filled surface competing with the submit button). Nothing else on the board uses accent. |
| Destructive | `#F0453D` (`--color-destructive`) | Not used by this phase's board UI. A misplay (fuse loss) is server-adjudicated and shown only as an updated fuse count (Body role, `--color-text`) — no destructive-red flash or confirmation dialog this phase; that reactive treatment is Phase 6 scope. Error/refusal frames reuse Phase 1's existing error handling, unchanged. |

**Own-hand slot (the load-bearing rule, HIDE-01/HIDE-03 visual requirement, restated from Phase 2's glyph-free precedent and made explicit for Hanabi's richer shape):**

A card in the viewer's own hand renders as a `--color-surface` filled tile with a `--color-border` outline containing **only its accumulated clue facts** — never a suit, a rank, a color derived from either, or any placeholder shape/icon that hints at identity (no card-back illustration, no "?" glyph, no colored border implying a clued suit). The tile's only visible content is:
- Zero or more small **clue-fact chips** (Label-role text, `--color-text`, on a `--color-border`-outlined chip background — reuse `--color-surface` for the chip fill so it doesn't read as a second "layer" of accent) showing positive clues received (e.g. "Rank 1" or "Red") and, at minimum, the slot's position number.
- If a slot has received no clues yet: the tile shows only its position number ("Slot 1"), nothing else — this is the empty state for an individual slot, not a placeholder glyph.

**Explicitly forbidden on an own-hand tile:** any suit name, rank number, or color swatch that is not itself the literal text of a clue the player has received. `possibleSuits`/`possibleRanks` (the narrowed-but-not-resolved candidate sets) are **not** rendered this phase — showing "could be Red, Yellow, or Green" is a memory-aid computation Phase 6 owns (UI-05); Phase 4 renders only the raw `positiveClues`/`negativeClues` arrays already on `ClueFactsView`, as plain fact chips ("Told: Red", "Told: not 3"). This keeps the rule mechanically simple to satisfy this phase: render only what was told, never anything computed or inferred, and never anything absent from the data — the server already guarantees no identity fields are present in a hidden `HanabiCardView`; the UI's job is to not visually reintroduce a signal the data doesn't carry.

**Other hands / played stacks / discard pile:** rendered face up — `--color-surface` tile, `--color-border` outline, suit+rank shown as plain text (Heading role, `--color-text`), e.g. "Blue 4". No color-coding by suit this phase (mapping suit to hue is a Phase 6/UI-06/UI-07 colorblind-safe-glyph decision this phase must not anticipate or half-build) — suit is identified by its written name only.

**Contrast rule:** unchanged from Phase 1/2 — accent fills always pair with `--color-bg` text/labels (≈10.9:1, WCAG AA pass), never `--color-text` (≈1.63:1, fails AA). Applies to the enabled play/discard/give-clue buttons, which reuse `Button variant="primary"` unmodified.

**Accent reserved for (explicit list, this phase):** enabled play/discard/give-clue submit button fill, own-turn indicator text, "you" hand-row ring (inherited), selected clue-target/clue-value ring (outline only, no fill). No other element uses accent.

## Screens & States (Phase 4 scope)

Single screen: **`HanabiBoard.tsx`**, rendered in place of `ForeheadCardGame.tsx` once `view.status === "in_progress"` (same mount point, `RoomClient.tsx`'s in-progress branch swap per CONTEXT.md's Integration Points). Reuses the existing page shell (centered flex column on `--color-bg`).

Layout, top to bottom:

1. **Turn indicator** (Body role) — accent-colored text on the viewer's own turn, `--color-text-muted` otherwise. `2xl` gap above, `xl` gap below.
2. **Other hands row(s)** — one row per other seat (`md` gap between rows), each row: seat label ("{displayLabel}'s hand", Label role, `--color-text-muted`) above a `sm`-gapped row of face-up card tiles rendered from that seat's **actual `cards.length`** (see Component Notes trap — never a hardcoded 5).
3. **Table** — a horizontal `xl`-gapped section containing, left to right: played stacks ("Played" heading + one column per suit in the active variant, `topRank` or "—"), discard pile ("Discard" heading + compact list or "No cards discarded yet"), and a token/counter cluster (clue tokens, fuse tokens, deck count — each its own Body-role line).
4. **Own hand** ("Your hand" heading, Label role) — `lg` gap above to visually separate from the table, a `sm`-gapped row of face-down slots rendered from the viewer's **actual `yourHand.length`** (4 or 5 depending on player count — never hardcoded).
5. **Action controls** — only meaningful, and only enabled per D-12, on the viewer's own turn:
   - A slot must be selected (click/tap a slot in step 4) before Play/Discard become actionable; selection state uses the accent ring (not fill).
   - Play/Discard buttons (`Button variant="primary"`, disabled per D-12's unambiguous cases: not your turn, discard at 8 tokens).
   - Give-clue control group: a seat picker (one button per other seat) + a color/rank value picker, then a "Give clue" submit button, disabled when it is not the viewer's turn, when zero clue tokens remain, or when the selected target+value combination touches zero of that target's **visible** cards (computable client-side from the already-received `otherHands` view — this is the one D-12 case requiring a small client computation, not a full `canClue` port).
6. **End-of-game state** — when the view indicates the game has ended (per D-13, the engine's `checkGameEnd` result surfaces via score/band on the view), all action controls in step 5 disappear entirely and are replaced by the "Game over" heading + "Final score: {score} — {band}" body. Hands, table, and tokens remain visible underneath exactly as they stood at the final turn (no new reveal-all content, no separate summary screen — mirrors Phase 2's end-state precedent).

No other screens change this phase. Lobby, join, create-room, and refusal screens are untouched (Phase 1 scope, already approved).

## Component Notes

- **No new shared design-system components required.** `Button` (primary/ghost, unmodified) is reused for Play/Discard/Give-clue/seat-picker/value-picker exactly as the toy reused it for its guess buttons. A local `CardTile` component (face-up vs. face-down variants, following Phase 2's precedent) and a local `HandRow` component are reasonable file-level splits — both are phase-scoped under `apps/web/components/`, not additions to the Phase 1 design-system contract, and must not introduce colors, sizes, or weights outside the tokens declared above.
- **Trap 1 — hand size must never be hardcoded.** `HanabiView.yourHand` and every `otherHands[].cards` array are exactly as long as that hand's real size (4 cards for 4-5 player games, 5 for 2-3 — `handSizeFor` in `packages/rules/src/hanabi/variant.ts` already parametrizes this server-side). The board MUST render slots via `.map()` over the actual array, never a hardcoded 5-slot grid. A hardcoded grid would silently misrender in every 4-5 player game and is exactly the kind of bug this spec exists to prevent visually reintroducing.
- **Trap 2 — stable `data-testid` hooks are required, not optional.** Playwright specs for RT-01 and RT-03 assert against this screen across two browser contexts and a mid-game reload; a `data-testid` must exist and remain stable across implementation detail changes for at minimum: `turn-indicator` (reused from the toy), `own-hand`, `own-hand-slot-{n}`, `other-hand-{seatId}`, `other-hand-card-{cardId}`, `played-stack-{suit}`, `discard-pile`, `clue-tokens`, `fuse-tokens`, `deck-count`, `play-button`, `discard-button`, `clue-target-{seatId}`, `clue-value-{value}`, `give-clue-button`, `game-over-heading`, `final-score`. This list is a floor, not a ceiling — add more if a specific assertion needs finer granularity, but do not remove or rename any of these without updating the e2e specs in the same change.
- **Own-hand tile is deliberately blank of identity, not blank of information.** Unlike Phase 2's fully-empty face-down placeholder (no game-relevant state to show), a Hanabi own-hand slot legitimately has clue facts to render — the rule is narrower than Phase 2's "no glyph at all": render clue facts and position only, never identity or identity-adjacent signal (see Color section for the exact boundary).
- **Suit is text, not color, this phase.** Do not map any `Suit` value to a hue for other-hand/stack/discard rendering — that is Phase 6/UI-06/UI-07's colorblind-safe-glyph-and-luminosity design work, and pre-empting it here with an ad hoc color mapping would be exactly the kind of half-built work CONTEXT.md warns against ("premature attachment").
- Use `clsx` for conditional class composition (selected-slot ring, disabled button states, own-turn accent text) per `CLAUDE.md`'s locked stack — no `tailwind-merge` needed at this phase's component complexity.
