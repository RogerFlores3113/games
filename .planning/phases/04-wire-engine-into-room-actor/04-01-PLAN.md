Create `packages/schema/src/games/hanabi.ts`, copying `forehead-card.ts`'s file-header comment block and adapting it: state that every object schema is `z.strictObject` declared independently at EVERY nesting level (never `.omit()`/`.extend()`/`.partial()`), that this module is imported ONLY by `apps/worker`'s `game-registration.ts`, that it is never re-exported from `packages/schema/src/index.ts` (FDN-01), and that `packages/rules` never imports it (FDN-02).

Declare, each as its own named const: `SuitSchema` as `z.enum` over the exact seven ALL_SUITS values; `RankSchema` as a union of `z.literal(1)`..`z.literal(5)`; `ClueValueSchema`; `ClueFactsViewSchema`; `HiddenCardViewSchema`; `VisibleCardViewSchema`; `HanabiCardViewSchema`; `OtherHandSchema`; `StackViewSchema`; `DiscardCardSchema`; the four history branch schemas; `HistoryEntryViewSchema`; and the exported `HanabiViewSchema`.

`ClueValueSchema` MUST be a single `z.strictObject` with `type: z.enum(["color","rank"])` and `value: z.union([SuitSchema, RankSchema])` — deliberately NOT a `z.discriminatedUnion("type", ...)`. Add an inline comment giving the reason: `ClueFactsView.positiveClues`/`negativeClues` and `HistoryEntryView`'s clue branch are declared in `state.ts` as the loose shape `{ type: "color" | "rank"; value: Suit | Rank }`, which is not assignable to a narrower discriminated union, so a discriminated union here would make `game-registration.ts`'s `[HanabiView] extends [HanabiViewWire]` assertion evaluate to `never` and fail to compile. Note in the same comment that this is a view-shape concession only and does not weaken redaction, because the own-hand boundary is carried by the `hidden` discriminant below.

`HanabiCardViewSchema` MUST be `z.discriminatedUnion("hidden", [HiddenCardViewSchema, VisibleCardViewSchema])`. `HiddenCardViewSchema` carries exactly `id`, `hidden: z.literal(true)`, and `facts` — it must never mention `suit` or `rank`. `VisibleCardViewSchema` carries `id`, `hidden: z.literal(false)`, `suit`, `rank`, `facts`. `HistoryEntryViewSchema` MUST be `z.discriminatedUnion("type", [...])` over the four independently declared strict branches.

Bound the numeric fields to their real engine ranges: `clueTokens` int 0-8, `fuses` int 0-3, `stacks[].topRank` int 0-5, `deckCount` and `score` nonnegative ints, `finalTurnsRemaining` a nullable nonnegative int. `variant` is `z.enum(["base","rainbow","black"])`. `yourSeatId` is `z.string().nullable()`.

Export `HanabiViewSchema`, `export type HanabiViewWire = z.infer<typeof HanabiViewSchema>`, and `export const HANABI_GAME_ID = "hanabi" as const` (matching `hanabiGame.id` in `packages/rules/src/hanabi/adapter.ts:19`).

Then wire the subpath in three places, mirroring the existing `forehead-card` entries exactly and leaving those entries in place: add `"./games/hanabi": "./src/games/hanabi.ts"` to `packages/schema/package.json`'s `exports`; add `"@games/schema/games/hanabi": ["packages/schema/src/games/hanabi.ts"]` to `tsconfig.base.json`'s `paths` ABOVE the bare `"@games/schema"` key; and add `"@games/schema/games/hanabi"` to the alias block of ALL FOUR Vitest projects (schema, rules, worker, web), each time ordered BEFORE the bare `"@games/schema"` key, because Vite matches aliases by prefix in insertion order.
