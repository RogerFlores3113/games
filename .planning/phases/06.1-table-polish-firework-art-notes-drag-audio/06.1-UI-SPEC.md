## Spacing Scale

Inherited verbatim from Phase 1/6 (`apps/web/app/globals.css` `--space-*` tokens) — do not redefine:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Note-chip internal padding, corner-numeral offset, pip gaps |
| sm | 8px | Note chip-to-card gap, marks-zone internal spacing |
| md | 16px | Default element spacing (unchanged) |
| lg | 24px | Section padding (discard-overlay panel padding) |
| xl | 32px | Layout gaps (unchanged) |
| 2xl | 48px | Major section breaks (unused this phase) |
| 3xl | 64px | Page-level spacing (unused inside the fixed game view) |

Exceptions:
- `--size-touch-min: 44px` (inherited) — every clickable control, **including the new note chip, mute toggle, and discard-view toggle**, uses a 44×44px minimum click target, even though the chip's visible glyph is small (D-05's constraint that the marks zone must preserve the 1280×720 no-scroll fit governs the chip's *visual* footprint, not its *click* target — pad the hit area invisibly, matching the existing pattern of small glyphs inside larger touch-target buttons already used by `OwnHandCard`/`TeammateCard`).
- **New this phase:** the drag-active card (the one being dragged) is exempt from the normal card-frame box-shadow rules while mid-drag — it renders at a `1.05x` scale with an elevated `box-shadow` (see Drag & Drop below) as a state, not a new spacing token.
- **New this phase:** marks-zone height above each card is fixed at `28px` (own-hand and teammate alike) regardless of whether it currently holds clue marks, a note chip, both, or neither — this is a visual-artifact size (like Phase 6's card dimensions), not a 4px-scale spacing token, chosen so the D-05 "preserve 1280×720 no-scroll fit" constraint holds with a constant band height rather than one that grows/shrinks per card.

## Color

Palette: dark "fireworks night" (unchanged base, Phase 1 D-16 / Phase 6 extension). Phase 6.1 **extends** `apps/web/app/globals.css`'s `@theme` block only as needed for the new burst-art rework; it does **not** redefine `--color-bg`, `--color-surface`, `--color-accent`, `--color-destructive`, `--color-text`, `--color-text-muted`, `--color-border`, `--color-status-connected`, `--color-status-disconnected`, or any of the seven `--color-suit-*` hue tokens, or `--color-card-glow` — all inherited unchanged from Phase 6.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0F1A` (`--color-bg`, inherited) | Page/board background, now layered under ART-02's city-at-night image (see Background below) rather than a flat fill |
| Secondary (30%) | `#141A2E` (`--color-surface`, inherited) | Card backgrounds, note-chip background, discard-overlay panel background |
| Accent (10%) | `#F5B942` (`--color-accent`, inherited) | **Reserved list extended by exactly one new use this phase:** the note-chip's focused/editing outline (reuses the existing "focus rings on all interactive controls" reserved use — not a new category). No other new accent use. Drag-drop-zone highlight, mute toggle, and volume slider explicitly do **not** use accent (see below) to keep the reserved list from creeping. |
| Destructive | `#F0453D` (`--color-destructive`, inherited) | Unchanged — fuse-lost flash / discard drop-zone invalid-state text only. The discard *drop zone* itself while a valid drag hovers it uses `--color-card-glow` (a neutral "valid target" signal, matching the existing clue-preview highlight language), not destructive-red, since dropping to discard is a normal legal action, not a dangerous one. |

**Drop-zone highlight (new, D-16):** both the stacks area (play zone) and discard pile (discard zone) reuse the **existing transient clue-touch highlight visual language** (`box-shadow: 0 0 0 3px var(--color-card-glow)`, already defined in `globals.css`) while a valid drag hovers them, and the **existing D-18 disabled-reason copy pattern** (`--color-text-muted`, Label role, inline text) when the zone is not currently a legal drop target. No new color token — this deliberately reuses `--color-card-glow`, never introduces a "valid-drop-green" or similar new semantic color.

**Note chip states (new, no new token):**
- Empty: `--color-border` outline, `--color-text-muted` placeholder icon.
- Populated: `--color-surface` fill, `--color-border` outline, `--color-text` label text.
- Editing (focused): `--color-accent` outline (reserved-use extension above).

**Background overlay (ART-02, D-14):** the city-at-night image sits behind the existing `--color-bg`-toned board via a dark scrim — `background: linear-gradient(rgba(11,15,26,0.75), rgba(11,15,26,0.75)), url(...)` (or an equivalent overlay div) — derived from `--color-bg` at 75% opacity, the same "derive a scrim from an existing token" pattern Phase 6's `EndOverlay` already established at 70%. No new color token; the overlay strength (75%, slightly stronger than the EndOverlay's 70%, since it must sit *behind* live gameplay UI rather than dim a paused screen) is Claude's Discretion per CONTEXT.md and is tunable at owner sign-off (D-14).

**Accent reserved-for list (explicit, extended from Phase 6, still exhaustive):** primary CTA fill ("New game" only, in-game), room-code Display text (not used in-game), own-seat "you" ring, active-turn hand-container ring/glow, own-hand "Your turn" state accent, focus rings on all interactive controls (now explicitly including the note chip's editing state). Nothing else uses `--color-accent`.

## Layout — New Zones

Extends Phase 6's fixed three-band desktop layout (`apps/web/.../06-UI-SPEC.md` §Layout) — **band structure, heights, and the 1280×720 no-scroll target are unchanged and must be preserved** (D-05 explicit constraint). Only the following are new:

### Marks zone (NOTE-01, replaces Phase 6's in-card candidate strip position)

- A fixed **28px-tall zone directly above every card** (own-hand and teammate alike), containing: positive/negative clue marks (Phase 6 D-12/D-13 content, relocated here per D-07) on the left/center, and — **own-hand cards only** — the note chip on the right edge of the same zone.
- This zone is additive to each card's existing footprint; card body dimensions themselves (Phase 6's 56×78 / 72×100 / 48×64 sizing table) are unchanged. The 28px zone height is accounted for inside Phase 6's existing per-band height budget (top band 168px, bottom band 208px) — the executor must re-verify the no-scroll fit at 1280×720 once the zone is added, per D-05's explicit instruction, and may tighten `--space-xs`/`--space-sm` gaps elsewhere in the band (following Phase 6's own precedent of tightening spacing for viewport fit) rather than growing the band.

### Drop zones (HAND-02)

- **Play zone** = the existing center-band stacks area (Phase 6 Table.tsx region) — no new DOM region, an existing region gains drop-target behavior.
- **Discard zone** = the existing center-band discard pile — same principle.
- Both zones highlight (per Color §Drop-zone highlight above) only while a drag is in progress and the zone is currently a legal target for the dragged card; both show existing D-18 disabled-reason text when illegal.

### Discard overlay panel (D-13)

- `position: fixed; inset: 0;` scrim + centered panel, structurally identical to Phase 6's `EndOverlay` pattern (`--color-surface` background, `--color-border` border, `--space-lg` padding) — reused for consistency, not invented fresh. Opens on click of the compact discard's toggle, closes on click-outside, close-button click, or Esc. Layout never shifts underneath it (D-13 explicit requirement) since it is an overlay, not an inline expansion.

### Audio controls

- Mute toggle + volume slider live in the **bottom band's controls row**, alongside the existing Play/Discard/Give-clue buttons (same row, right-aligned, per Claude's Discretion on placement) — icon-only, 44×44px touch targets, no new band.

### Background (ART-02)

- City-at-night image + scrim (per Color §Background overlay above) replaces the flat `--color-bg` fill at the `<body>` or outer `<main>` level — `background-size: cover`, `background-position: center`, `background-attachment: fixed` (static, no parallax/motion per D-14). Image file lives under `apps/web/public/` with a co-located credit/license file (source URL, author, license) per D-14's explicit requirement.

## Suit Art Rework (ART-01, replaces Phase 6 Suit Identity System)

Phase 6's geometric-glyph table (star/triangle/square/circle/diamond/starburst/notched-hexagon) is **reworked in place** inside `apps/web/lib/suit-visuals.ts` (single source, per D-08 — rework, don't fork) into firework-burst silhouettes. The **rendering rule is unchanged**: glyph + hue always paired, never hue alone; static literal class/style lookup, never runtime-interpolated Tailwind classes (Phase 6's binding implementation constraint carries forward unchanged).

| Suit | Hue token (unchanged) | Burst treatment (new, replaces old glyph) |
|------|------------------------|--------------------------------------------|
| Red | `--color-suit-red` | Radiating spike burst (classic firework "chrysanthemum" silhouette) |
| Yellow | `--color-suit-yellow` | Dense round-petal burst, more petals/rounder tips than Red so silhouette reads distinctly in grayscale |
| Green | `--color-suit-green` | Ring/willow-trail burst (a hollow-center ring of short trailing spikes) — structurally distinct outline (donut-like) from Red/Yellow's solid radial fills |
| Blue | `--color-suit-blue` | Cross/star-burst with four dominant long spikes + four short ones (asymmetric spike-length pattern, distinct from Red's uniform 10-point star) |
| White | `--color-suit-white` | Sparse wide-angle burst (fewer, longer, thinner spikes — the "sparkler" silhouette) — lightness is still carried by hue per Phase 6 Pitfall-1-style reasoning, but shape is the primary carrier |
| Rainbow | `--color-suit-rainbow` | Largest burst silhouette, flat single-tone fill (no gradient in the silhouette itself, decorative multicolor ring only as garnish around it) — carries forward Phase 6's Rainbow rule verbatim, now expressed as a burst rather than a starburst-glyph |
| Black | `--color-suit-black` | Compact double-ring burst (two concentric rings of short spikes) — rendered light silver per Phase 6's carried-forward rule ("blackness" is name/shape, never literal darkness) |

**Rank display (D-09):** burst **count** conveys rank (a rank-3 card shows three small bursts arranged box-game-style), **plus** a small corner numeral (reusing Phase 6's existing numeral typography/positioning pattern) as the fast read — both signals present on every face-up card and stack head; corner-numeral-only is used at the smallest sizes only if execution finds burst-count illegible at 48×64px stack-head size (Claude's Discretion, flagged for verification against Phase 6's contrast/legibility testing pattern — `suit-visuals.test.ts` equivalent should assert legibility, not just color contrast, for this new count-based encoding).

**Own face-down card back (D-10):** single neutral firework-themed card-back motif (unlit shell / night silhouette), identical across every own-hand slot regardless of the card's true identity — zero identity signal, replacing Phase 6's "blank outline square" placeholder with a themed but equally information-free design.

**Art source (D-11):** hand-authored inline SVG, `apps/web/lib/suit-visuals.ts` remains the single module (reworked, not forked); path data colored exclusively via existing `--color-suit-*` `@theme` hue tokens — no hex literal outside `globals.css`'s `@theme` block, carrying forward Phase 1/6's binding rule.

**Art reach (D-12):** applies everywhere — face-up cards, stack heads, discard entries (both compact-count and expanded-overlay views), color-clue picker buttons, clue marks, candidate strips.

**Owner sign-off gate (D-31):** per CONTEXT.md, burst silhouettes must be shown to the owner before being built into cards — this UI-SPEC's shape descriptions above are the researcher's proposed defaults for that review, not a substitute for it. Do not treat this table as final until the owner confirms.

## Drag & Drop Interaction (HAND-01, HAND-02)

- **Trigger:** `pointerdown` on an own-hand card starts a drag (mouse only, per D-20 — no touch-action handling required this phase, but the implementation should not structurally preclude adding `touch-action` support later, per D-20's explicit "should not preclude touch later" instruction).
- **Visual during drag:** dragged card renders at `1.05x` scale with an elevated `box-shadow` (reuses the existing luminosity "Known" step's shadow intensity as a starting point, scaled up slightly), following the pointer; the vacated slot in the hand shows a dashed `--color-border` placeholder outline (matching existing border-token usage, no new token) so hand layout doesn't jump.
- **Drop resolution (D-15):** releasing over a valid zone (another own-hand slot = reorder; stacks area = play, only on own turn; discard pile = discard, only on own turn and only when discard is legal per existing D-18 rules) acts **immediately**, no confirmation. Releasing outside any valid zone snaps the card back to its original slot with a short CSS transition (respecting `prefers-reduced-motion`, consistent with Phase 6's existing motion-reduction pattern).
- **Fallback controls (HAND-02):** existing Play/Discard buttons (`data-testid="play-button"`, `data-testid="discard-button"`, preserved verbatim from Phase 6) remain fully functional and are the only path for keyboard users (D-19 — no keyboard reorder path this phase, an explicit exception to Phase 6 D-19 recorded in CONTEXT.md).
- **Remote view (D-18):** teammates see only the end result (new order, or the play/discard outcome) — no in-progress drag streaming, no "X is dragging…" message, consistent with keeping the wire protocol quiet (CONTEXT.md explicit: no new spammy history entries).
- **Fly-to animation (D-21):** when a card leaves a hand via play/discard (by drag or button), every screen **except the dragging player's own** plays a short fly-to animation from the hand slot to the stack/discard location — reuses Phase 6's existing CSS-keyframe + `prefers-reduced-motion` degrade pattern (instant style swap, no animation, signal still visible). The dragging player's own drop motion *is* their fly-to (no redundant second animation on their screen).
- **Slot-preserving draw (HAND-03):** the newly drawn card renders directly into the vacated index — no reflow/append animation distinct from the fly-to above; this is a rendering-order guarantee (engine-level, `packages/rules/src/hanabi/actions.ts`), not an additional visual effect.

## Audio Cues (AUD-01)

| Event | Cue character (D-24, "soft, minimal, plastic/ceramic tile-noise themed") |
|-------|----------------------------------------------------------------------------|
| Clue given | Short, soft tap/click (single tile touch) |
| Card played (non-completing) | Slightly warmer/rounder tap than the clue cue, distinct enough in timbre to not be confused with it |
| Card discarded | Duller, lower-pitched tap (a "set down" feel, distinct from play's brighter tap) |
| Fuse lost | A distinct minor/dissonant short tone — plays *instead of* the play cue on a misplay, never both (D-24 explicit: misplay plays the fuse cue only) |
| Stack of five completed | A brighter, slightly longer multi-tap or chime flourish — plays *instead of* the play cue on the completing play (D-28 explicit: completion-only, not play-then-completion) |

- **Synthesis:** Web Audio API oscillators/short envelopes, no audio files (D-25) — zero licensing surface, zero new asset weight.
- **Controls:** mute toggle + volume slider, bottom-band controls row (Layout §Audio controls above), state remembered per browser (localStorage, matching the notes-persistence pattern's storage mechanism).
- **Autoplay policy:** the audio context is created/resumed on first user interaction (D-26) — no sound attempts before a click/keypress has occurred anywhere on the page.
- **Trigger scope (D-27):** every action's cue plays on every connected screen, not just the acting player's.
- **No catch-up audio (D-29):** cues are derived from new `history` entries arriving live after the WebSocket connection is established — initial load, refresh, and reconnect catch-up never play a backlog of cues, even if multiple actions occurred while disconnected.

## Notes (NOTE-02)

- **Storage:** browser `localStorage`, keyed by room + seat + card id (D-02) — never sent to the server, no new wire message, no schema change. Storage access wrapped defensively (try/catch; a full or disabled localStorage must not crash the board — the notes feature degrades to "notes don't persist" rather than breaking gameplay).
- **Scope:** own hand only (D-03); no note affordance renders on a teammate's card.
- **Lifecycle:** keyed to card id so a note follows its card through reorder (D-04); deleted the instant the card leaves the hand (played/discarded); a newly drawn card into that slot starts blank. Stale entries for ended/abandoned games may be pruned opportunistically (not a hard requirement this phase).
- **Editing UI:** small chip in the marks zone (Layout §Marks zone above), click to type inline, `~20` character cap enforced at the input (D-06) — a `maxLength` attribute plus visual truncation-safe layout (chip width sized for the character cap, no ellipsis needed since content never exceeds it).
- **Accessibility:** chip is a real `<button>` that becomes an `<input>` (or toggles to one) on activation, keyboard-reachable, `aria-label="Add note"` when empty per Copywriting Contract above.
