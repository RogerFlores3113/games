# Phase 6.1 Plan 01: Engine Changes for Slot-Preserving Draw and Reorder Summary

Slot-preserving draw (a played/discarded card's replacement now lands in the exact vacated hand index) and a new server-validated `reorder` action (an exact-permutation-only, off-turn-legal hand reorder) added to the Hanabi rules engine, with full TDD unit coverage and no wire-schema or `AdapterError` widening.

## What Was Built

**Task 1 — Slot-preserving draw (HAND-03):** `drawCard` in `packages/rules/src/hanabi/actions.ts` now takes an `insertAtIndex` parameter and inserts the newly drawn card at that index via `slots.slice()` + `.splice()`, instead of appending to the end. `applyPlay` and `applyDiscard` both capture the removed card's index from `state.hands` (pre-removal, via a new private `findHandIndex` helper) *before* calling `removeFromHand` — this ordering is the exact fix for RESEARCH.md's named Pitfall 1 (computing the index after `.filter()`-based removal would silently shift it). No-draw paths (empty deck, final round already running) are unchanged: the hand simply shrinks, preserving the relative order of surviving cards.

**Task 2 — Server-validated reorder action (HAND-01):** `HanabiAction` gained a fourth union member `{ type: "reorder", cardIds: readonly string[] }`. `canReorder` (legality.ts) validates `cardIds` is an exact permutation of the actor's current hand ids (length match, no duplicates via Set-size comparison, full membership check), rejecting any mismatch with the existing `card_not_in_hand` reason — no new `AdapterError` member was added. `canReorder` deliberately omits the `isActorsTurn` check per D-17 (reorder is legal off-turn, spends no resource). `isReorderRequest` in actions.ts follows the identical exact-own-key guard discipline as `isPlayRequest`/`isDiscardRequest`/`isClueRequest`. `applyReorder` rebuilds only the actor's hand in the submitted order (matched by card id, preserving each card's existing `facts`), leaving turn index, clue tokens, fuses, deck, stacks, discard, final-round counter, history, and every other seat's hand completely untouched. `index.ts` re-exports `canReorder` alongside the other legality predicates it already exported.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking issue] Fixed a property-test type-narrowing gap exposed by the widened `HanabiAction` union**
- **Found during:** Task 2 verification (`npx tsc -b packages/rules apps/worker apps/web`)
- **Issue:** `conservation.property.test.ts`'s action-type narrowing used `if (play) ... else if (discard) ... else { access targetSeatId/clue }`. Adding the fourth `reorder` member to `HanabiAction` meant the `else` branch's type no longer narrowed to only `clue` — TS2339 on `action.targetSeatId`/`action.clue`, a blocking compile error under the plan's own verification command.
- **Fix:** Changed the final `else` to an explicit `else if (action.type === "clue")`, with a comment noting `enumerateLegalActions` (test-support.ts, unchanged this plan) never generates a `reorder` action, so no new test behavior was needed — this is a type-level fix only.
- **Files modified:** `packages/rules/src/hanabi/conservation.property.test.ts`
- **Commit:** `10faf81`

### Notes (not deviations, flagged for transparency)

- One of Task 2's acceptance-criteria greps (`grep -v '^\s*//' actions.ts | grep -c "\.\.\.state"` expected to output `0`) actually outputs `2`, matching two **pre-existing** array-spread expressions (`[...state.discard, card]` in `applyPlay`/`applyDiscard`, both present before this plan). These are array spreads used to append to the discard pile, not the object-literal `{ ...state, ... }` HanabiState-spread the no-spread discipline (and this grep) is meant to catch — the grep pattern is broader than the rule it's checking. `applyReorder` and the modified `drawCard` both use field-by-field literal construction, matching the rule's actual intent. Left as-is since fixing the pre-existing array-spread lines is unrelated to this plan's scope.
- Per RESEARCH.md's own suggestion, the three property-test files (`conservation`, `redaction`, `termination`) and `test-support.ts`'s `enumerateLegalActions` were **not** extended to generate `reorder` actions — this was intentionally out of scope per the plan's `files_modified` list, which names only `state.ts`, `legality.ts`, `legality.test.ts`, `actions.ts`, `actions.test.ts`, and `index.ts`. Reorder's conservation/redaction/termination invariants are covered by the targeted unit tests in `actions.test.ts`/`legality.test.ts` instead (every field left untouched, facts preserved, no leak surface introduced). A future plan may extend the property-test arbitraries if deeper property coverage of reorder is desired.
