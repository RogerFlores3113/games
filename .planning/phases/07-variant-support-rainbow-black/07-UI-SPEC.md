# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Scope is deliberately tiny (07-CONTEXT.md "Phase Boundary"): one new interaction (the rainbow tile's quick-clue colour row) reusing every token, component and copy pattern already approved in the Phase 6 / 6.1 / 6.2 UI-SPECs and the owner's seven 06.2 UAT review rounds. This document does not redeclare the whole design system — it declares what's new, and points at the frozen contracts it must not violate.

## Typography

Inherited verbatim from Phase 1/6/6.2 — **do not redefine, do not introduce a third size or a bespoke smaller size for the colour row**:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.5 |
| Heading | 24px | 600 (semibold) | 1.2 |
| Display (room code only) | 40px | 600 (semibold) | 1.2 |

**This phase's only typographic decision:** each colour-row entry reuses the popover's existing single-colour-button styling exactly — `text-[length:var(--text-label)]` (14px, weight 600 inherited from the `role="menuitem"` button's own classes), rendered in that suit's own `--color-suit-*` hue via `style={{ color: suitVisual.hueVar }}`, **not bold** (bold is reserved for the rank button below, unchanged, per the owner's verbatim gap-16 spec: "the number being a bold, always below the color hint"). No new size is introduced for five entries versus one — if the five full colour names (`Red`, `Yellow`, `Green`, `Blue`, `White`) risk crowding, the layout response is wrapping and/or a wider popover with the anchor clamped/flipped (see Layout), never shrinking text below 14px (the `--text-label` floor, per CONTEXT.md's explicit instruction).

## Color

Palette: dark "fireworks night" (unchanged, Phase 1 D-16). **This phase adds zero new tokens.** Every colour used by the new colour row is one of the seven existing `--color-suit-*` tokens, already defined in `apps/web/app/globals.css`'s `@theme` block and already AA-verified against both `--color-bg` and `--color-surface` (Phase 6 UI-SPEC Color section, unchanged):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0F1A` (`--color-bg`, inherited) | Page/board background — untouched |
| Secondary (30%) | `#141A2E` (`--color-surface`, inherited) | Popover background (`backgroundColor: "var(--color-surface)"`, unchanged from the existing `CluePopover`) |
| Accent (10%) | `#F5B942` (`--color-accent`, inherited) | **Reserved list unchanged, no new use added by this phase** — focus rings on the new colour-row buttons reuse the existing accent focus-ring pattern, not a new reservation |
| Destructive | `#F0453D` (`--color-destructive`, inherited) | Unchanged, not used by this phase |

**New this phase — reuse, not new tokens:** the rainbow tile's colour row renders each of the five nameable colours (`red`, `yellow`, `green`, `blue`, `white`, in `cluableColors` order per D-05) using its own existing `SUIT_VISUALS[suit].hueVar` — the exact same `--color-suit-*` token each colour's single-colour button already uses everywhere else on the board (stack heads, glyphs, single colour button on a non-rainbow tile). No hex literal appears anywhere in this phase's code; every colour reference is `var(--color-suit-*)`, matching the project's standing "no hex outside `@theme`" rule (CONTEXT.md, reaffirmed).

**Black stays silver, unchanged (owner decision, 2026-09-18):** `--color-suit-black` remains `#B7C2D6`, no redraw, no hue shift. A black tile's popover is untouched — a single "Black" colour button exactly as today (D-08), since Black is a nameable colour like any other suit. This phase does not touch `suit-visuals.ts`'s Black entry at all.

**Rainbow itself never gets a colour-row entry or a colour button of its own** — "Rainbow" must never appear as a clickable colour option anywhere (RULES-14, D-01, owner-locked). The row lists only the five nameable colours; rainbow's own tile identity continues to render via its existing multicolour gradient fill (`--color-suit-rainbow` as the gradient's final stop, unchanged from `suit-visuals.ts`).

## Layout

**No change to board geometry.** This phase's one interaction lives entirely inside the existing `CluePopover` — an absolute overlay (`position: absolute`, `top: 100%`, centered via `transform: translateX(-50%)`) anchored to the clicked tile's `position: relative` wrapper (`TeammateCard.tsx`'s `<span data-clue-tile>`). It adds **zero flow height** to the board and must never affect any of the fixed reserved regions the 06.2 "fixed board geometry" gap (gap 1) locked in — Play area, Discard area, token column, own-hand band, teammate band are all untouched by this phase.

**Colour-row layout (Claude's discretion per CONTEXT.md, decided here):**
- Default: a single horizontal row of five colour buttons, each sized to its own text content (no fixed width), separated by `--space-xs` (4px) gaps, inside the popover's existing `flex-col` — i.e. the row is one `flex flex-row flex-wrap` element that becomes the popover's first child, replacing the single colour `<button>` only when the clicked tile's suit is not in `cluableColorsForView(game)` (the rainbow case; see Component Notes for the exact detection rule).
- If five full-name labels (`Red Yellow Green Blue White`) overflow the popover's available width at a hand edge (1280px floor, per UI-11's worst case), the row **wraps to a second line** (`flex-wrap`) rather than shrinking text size — this is the "minimal, non-decorative" response consistent with the owner's minimalism pattern across 06.2's seven review rounds (no new visual chrome, no truncation, no tooltip).
- **Horizontal anchor clamping (mandatory, per CONTEXT.md):** the popover's existing centered anchor (`left: 50%; transform: translateX(-50%)`) must clamp or flip near the viewport's left/right edges so the wider five-colour popover never clips outside the 1280×720 floor when the clicked tile sits at the far left or right of a hand row. This is a new requirement the single-button popover never needed (64px `minWidth` never came close to an edge); the wider row can. Implementation is free (CSS `clamp()`, a JS-measured offset, or a `flip`/`shift` middleware-style adjustment) as long as the popover's own geometry is the only thing that moves — it must never push, resize, or reflow any other board element.
- The popover's `minWidth: 64` on the existing style object no longer describes the rainbow case; the executor should treat that as the single-colour-button floor only and let the colour row's own content set its width beyond that floor.

**Nothing else in the board's layout changes.** No new band, no new fixed region, no change to `layout-budget.ts`'s constants (`MAX_SUITS`, `TEAMMATE_BAND_PX`, `OWN_BAND_PX`, etc.) — this phase's UI change is a strict subset of the existing popover's footprint, scaled by content, not a new layout primitive.

## Interaction Contract — Rainbow Tile Colour Row (D-05..D-08, owner-confirmed 2026-09-18)

This is the phase's one new interactive surface. Everything below is locked (owner-approved, not a Claude default):

1. **Trigger:** clicking any visible (non-hidden) teammate tile opens its `CluePopover`, exactly as today. No change to when or how the popover opens.
2. **Variant-agnostic detection (binding, D-05/06.1-established pattern):** the popover shows the colour **row** instead of the single colour **button** when the clicked tile's own suit is **not** in `cluableColorsForView(game)` — never a literal `suit === "rainbow"` check. This is the only correct way to detect "this suit isn't itself a nameable colour" and keeps the code correct if a future variant ever added a second non-nameable suit, without special-casing rainbow by name.
3. **Row contents:** exactly the variant's `cluableColors`, in that array's order (`red, yellow, green, blue, white` for both base and Rainbow — Black's `cluableColors` includes `black` itself, which is why Black never triggers the row, see point 2). Each entry is a `<button role="menuitem">` labelled with that suit's `SUIT_VISUALS[suit].label`, styled with `color: suitVisual.hueVar`, at the Label typography role (14px/600), **not bold**.
4. **Number button:** unchanged, stays below the row, bold, same styling and position as today.
5. **One click sends:** clicking a colour-row entry dispatches an ordinary colour clue for that suit (`{ type: "color", value: suit }`) to the clicked tile's owning seat — the exact same `onGiveClue` callback the single-colour button already uses, just parametrized by which colour was clicked instead of always the tile's own suit. No confirmation step, matching the existing single-button behaviour.
6. **Non-rainbow tiles are unchanged.** A red, yellow, green, blue, white, or black tile keeps exactly today's single colour button. In Rainbow, a red tile's own "Red" button still also touches any rainbow tiles in that hand — correct engine behaviour, no UI preview or special-casing needed (D-06).
7. **Disabled gate (D-07, gap-15 minimalism, binding):** every colour-row entry shares the exact same `disabledReasonFor`-derived gate the rank button already uses (game ended, reconnecting, not-your-turn, no clue tokens) — **no entry is ever individually disabled**, because every nameable colour always touches a clicked rainbow tile by the engine's own rule. **No disabled-reason text is shown for the row or any entry within it**, matching gap 15's "delete the disabled-reason text" instruction, which already applies to this popover.
8. **Black stays a single button (D-08):** no code change to the black-tile path. Its `cluableColors` includes `black`, so `cluableColorsForView(game).includes("black")` is true and the single-button branch renders exactly as it does today.

**Hint display, unaffected (D-09/D-10):** a rainbow tile touched by (for example) a red clue shows the same red-ring hint indicator every other suit's tile shows when touched by that colour — no change to `hanabi-hint-logic.ts` or `HintIndicator.tsx`. This phase adds no new visual state to the hint system, only a new way to *originate* a colour clue from a rainbow tile.

## Component Notes

- **`apps/web/components/hanabi/CluePopover.tsx`:** gains a new optional prop shape to render either the existing single colour button (unchanged) or a row of colour buttons (new). The exact prop shape (e.g. `colorOptions: readonly Suit[]` replacing the single `suit` for colour purposes, versus a new `colorRow?: readonly Suit[]` alongside the existing `suit`) is an implementation detail for the planner/executor — the binding constraint is behavioural (points 1-8 above), not the prop names.
- **`apps/web/components/hanabi/TeammateCard.tsx`:** computes whether to pass the row or the single button. The existing `colorNameable` boolean (`cluableColorsForView(game).includes(card.suit)`) already exists and already gates whether the *single* button is disabled (`!colorNameable`) — this phase's change is to also use `!colorNameable` (equivalently, `game.variant === "rainbow" && card.suit === "rainbow"` is explicitly **forbidden** as the detection method per CONTEXT.md's "Established Patterns") as the branch that swaps in the row instead of merely disabling the single button. When the row renders, every entry's disabled state resolves through the same `disabledReasonFor` call already made for the rank button (see D-07 above) — do not compute a fresh per-colour `disabledReasonFor` result whose only variable input is "clue touches nothing," since D-07 established that check can never fail for any nameable colour against a rainbow tile.
- **`apps/web/lib/hanabi-board-logic.ts`:** `cluableColorsForView` is reused as-is (no change needed) — it is already the single source for both the server-side-mirrored nameable-colours list and this UI's row contents.
- **No change to `apps/web/lib/suit-visuals.ts`** — Black's art and Rainbow's gradient/silhouette are both already correct and approved (06.1-07 owner sign-off); this phase's UI-07 verification work is test-only (asserting `glyphPath` uniqueness and gradient-fill rendering), not a design change.
- **No change to `apps/web/app/globals.css`** — zero new tokens, zero new hex values.
- **Own-hand identity boundary unaffected:** this phase's change touches only teammate-tile code (`TeammateCard.tsx`, `CluePopover.tsx`); no own-hand component is touched, so the existing `own-hand-source.test.ts`/`own-hand-render.test.ts` facts-only guards remain untouched and still apply unchanged.
- **E2E helpers** (`e2e/helpers.ts`): `giveAnyLegalClue`'s existing fallback-to-rank-clue behaviour for a disabled rainbow colour button must be updated once the row lands, so a Rainbow e2e run can give a colour clue from a rainbow tile through the real row instead of always falling back to rank. This is a test-harness change, not a design-contract item, but is called out here so the executor doesn't leave a stale comment describing pre-Phase-7 behaviour as current.
